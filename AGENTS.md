# Руководство для ИИ-агента (обязательно)

Этот файл — **контракт на реализацию**, а не рекламный README. Используй его вместе с документами в `docs/`. Непроверенное требование не считается реализованным.

## Приоритет источников

1. Этот файл: рабочий процесс, запреты, Definition of Done.
2. `docs/SMARTTHEIA_PROTOCOL.md`: wire format и состояния.
3. `docs/CONFIGURATION.md`: имена и семантика параметров.
4. `docs/IMPLEMENTATION_SPEC.md` + `docs/ARCHITECTURE.md`: функциональные требования и границы.
5. `docs/TUI_UX.md`: пользовательский контракт TUI.
6. `docs/IMPLEMENTATION_PLAN.md` + `docs/TESTING_CI.md`: порядок работ и качество.

Если требования конфликтуют, **не угадывай**: исправь противоречие отдельным документированным архитектурным решением (ADR), поддержи изменение тестом и обнови зависимые документы.

## Неизменяемые требования

- **Один конечный бинарник `theia`**; сервер и клиент — режимы одного приложения. Не создавать две поставляемые программы.
- **CI-only:** все тесты, smoke/E2E, системные и нагрузочные проверки, fuzz, security regressions и release benchmarks выполняются автоматически в GitHub Actions. Проверки на компьютере разработчика или пользователя не требуются и не являются доказательством готовности. Если сценарий нельзя выполнить автоматически, автоматизируй его в изолированном runner/VM: до этого требование остаётся незавершённым.
- **Rust**, асинхронная сеть на Tokio, TUI на ratatui, человекочитаемые TOML без БД и внешнего control plane.
- **Архитектура (spec v0.6, ADR-0086):** SmartTheia — собственный протокол, **SmartTheia XHTTP — единственный кастомный транспорт**, вдохновлённый Xray XHTTP, но не копия. Под ним стандартные HTTP/3 (QUIC) и HTTP/2 (TLS). Ровно два явных security modes на inbound: собственный SmartTheia REALITY (вдохновлён Xray REALITY, не копия; мастер или вручную) либо собственный TLS (только ручные cert/chain + private key). Никакого требования Xray/VLESS/XTLS wire/API/config совместимости или полного набора функций. Не вводить самодельные криптографические примитивы, TLS, HTTP/2 или QUIC.
- QUIC-first, H2-fallback **только по сетевой недоступности UDP/QUIC**, никогда вследствие отказа авторизации, ошибки сертификата или явной несовместимости протокола. Сохранять identity, security mode и XHTTP mode; нельзя молча ослаблять проверки.
- **BBR — P0:** на обоих QUIC endpoints фактически выбран и измерен BBR. Проверить API выбранного quinn/backend, не заменять молча алгоритм; без теста и замеров MVP не готов.
- **Browser TLS/HTTP interoperability and evidence — P0 (ADR-0074):** actual pinned browser runs are the only browser reference; H2/TLS and H3/QUIC are evaluated separately on Linux/Windows. Preserve independent strict CA/hostname/ALPN and authorization checks. uTLS comparison is retired, not a release prerequisite. H2/H3 functional Chromium coverage on Linux/Windows is confirmed (ADR-0076); browser wire/fingerprint parity remains open. Never claim byte-exact browser parity or DPI invisibility from a library, User-Agent or test result. No production wire/backend change in this migration.
- В первой поставке: Linux-сервер, Windows x64-клиент, локальные HTTP CONNECT/SOCKS5 и пользовательский Windows system proxy с восстановлением прежних параметров.
- Секреты не пишутся в логи или TUI в открытом виде (кроме явного одноразового confidential export с подтверждением). Примеры не содержат действующих ключей.
- **F-18/F-19 P0 (spec + M3.5a0 feasibility + M3.5b1 offline planner + M3.5b2a explicit strict H2 TLS probe, без режима/автоматического scanner):** криптографически аутентифицированный REALITY-подобный SmartTheia security mode, прозрачный двухшаговый серверный мастер подбора IP/domain с bounded opt-in active scans только разрешённых целей и anti-SSRF, независимая измеренная защита от TLS-in-TLS через flow shaping и classifier/performance E2E Linux/Windows. Не выдавать User-Agent/SNI/padding или единичный зелёный fingerprint test за готовую реализацию и не обещать гарантий DPI-невидимости. Не менять TOML/invite v1 без отдельного ADR и тестов; docs/STEALTH_REALITY.md и ADR-0020.
- **F-14 P0:** удалённая серверная TUI (через SSH/local IPC) создаёт пользователя с CSPRNG 32 bytes, явно назначает inbound grant и одноразово выдаёт секретный theia://v1 URI/file (единственный заменяющий формат SmartTheia XHTTP, без legacy compatibility, ADR-0087); сервер хранит только SHA-256. Клиентская TUI на Windows/Linux импортирует URI/file с безопасным preview, защищённым secret env/file store и строгим TLS trust; без автоматического connect/system proxy. Один бинарник для соответствующей ОС, но серверная и клиентская роли работают на разных машинах. Codec M4.4a не равен завершённому F-14.
- Каждый inbound имеет явный непустой список `allowed_user_ids`, глобальные пользователи не получают права по умолчанию. Auth: SHA-256 от декодированных 32 байт canonical base64url token, constant-time digest compare.
- Local CONNECT 200 / SOCKS5 success только после SmartTheia OPEN_OK; локальный listener ≠ авторизованный транспорт ≠ открытый туннель. При домене DNS выполняет сервер с ACL по закреплённому IP.
- Windows system proxy никогда не включается автоматически при запуске: только `manual` + TUI confirmation + сохранённый snapshot и безопасный CAS restore.

## Порядок работы с задачей

1. Выбери **крупный, логически связанный блок уровня законченного этапа** из `docs/IMPLEMENTATION_PLAN.md`: объединяй несколько взаимозависимых вертикальных срезов с общей целью и границей приёмки. Не дроби разработку на микроправки и отдельные PR ради формального прогресса; не объединяй несвязанные рискованные изменения только ради экономии CI.
2. Сначала сформулируй поведение (Given/When/Then), угрозы и отрицательные кейсы для всего блока.
3. Для каждого среза внутри блока сначала напиши регрессионные тесты, затем минимальную реализацию и рефакторинг. Обязательную проверку поведения и negative cases сохраняй; отдельный CI-прогон на каждое промежуточное изменение не требуется. Не заявляй red/green TDD evidence, если соответствующие состояния не были проверены в CI.
4. Собери код, тесты, TOML-примеры, wire-документацию, help/UX и ADR (если требуется) **в одном согласованном PR**. До отправки проверь полноту блока, согласованность контрактов и diff; промежуточные коммиты готовь в отдельной ветке без открытого PR или одним атомарным обновлением Git ref.
5. Запускай полный обязательный CI на итоговом состоянии блока, а не после каждого мелкого изменения. При падении собери связанные исправления по всем доступным результатам и отправь их одним пакетом; не запускай повторно заведомо неизменившиеся проверки без причины, если штатный CI позволяет безопасный rerun. Не перекладывай тесты на разработчика или пользователя. Пропуск, отмена или сбой обязательного job не являются успехом; merge разрешён только при зелёном `ci-gate` для актуального head SHA.
6. Не отправляй в CI отдельный исследовательский микросрез, небольшую группу тестов или документацию, если их можно включить в следующий общий этап. До публикации объединяй реализацию, негативные сценарии, границы безопасности, интеграцию, совместимость и документацию. Оценивай масштаб по завершённым требованиям и поведению, а не числу строк: не раздувай diff искусственно. Подготовительные изменения сохраняй без открытого PR; при уже красном CI исправления и связанные изменения отправляй одним обновлением, если это не затягивает срочный блокирующий дефект.
7. PR должен описывать: общую цель блока, что добавлено, что **ещё не реализовано**, миграции, тесты, риски, производительность. Отдельный небольшой PR допустим для срочного security fix, восстановления сломанного CI или независимого блокирующего дефекта; объясни причину.

## Код и архитектура

- DDD = понятные **bounded contexts**, не фабрики и интерфейсы ради интерфейсов. Границы из `docs/ARCHITECTURE.md` можно объединять, пока это упрощает код без ухудшения тестируемости.
- Зависимости направлены внутрь: чистый парсер/домен не зависит от TUI/сетевого IO. Использовать traits только при реальной смене реализации или для тестового шва.
- Избегать глобального изменяемого состояния, `unwrap` в обработчиках соединений, бесконечных очередей, блокирующего IO на Tokio.
- Ограничивать размеры фреймов, параллелизм, таймауты, количество открытых соединений, число ошибок аутентификации. Утечки ресурсов и panics — баги релиза.
- Не добавлять секреты в репозиторий, не отключать TLS verification, не хранить токены в командной строке.
- Код должен собираться под Windows; платформенный код изолировать через `cfg(windows)`.
- Функции включают явные типы ошибок; наружу отправляются безопасные коды, подробности остаются в локальной диагностике без секретов.

## Зависимости, CI, оптимизация

- Фиксировать версии в `Cargo.lock`; сначала выбрать минимальное количество зрелых crates. Проверять их API по текущей документации.
- `spikes/m0_1` — **изолированный исследовательский crate**, а не production workspace. Реальные Linux/Windows loopback тесты подтверждают HTTP/2 over TCP/TLS 1.3, HTTP/3 over QUIC/TLS, strict hostname/ALPN и активный BBR class на обоих peers. Контролируемый синтетический UDP drop test показывает recovery 768 КиБ, H2 credit-window тест подтверждает 1 МиБ/half-close, а Linux/Windows CI проходит 8 concurrent H2/H3 streams и единичную отмену stream с живым sibling request. Также проверена остановка и возобновление H2/H3 response при одном медленном читателе с ограниченными окнами, **без измерения peak RSS**. Дополнительно создан bounded default rustls ClientHello parser и H2/H3 engine-only baseline. Отрицательный тест проверяет отсутствие GREASE и обоих BoringSSL ALPS codepoints у текущего H2 rustls, он **не** доказывает реальный browser-like profile, см. `docs/adr/0005-tls-fingerprint-baseline.md`. Это **не** готовый proxy и **не** сравнительный P0 BBR RTT/jitter/throughput benchmark или uTLS-like profile. Перед переносом кода в один бинарник свериться с `docs/adr/0004-m0-1-feasibility.md`.
- **Rustfmt auto-repair:** если preflight успешно форматирует и обнаруживает изменения только tracked regular Rust files, старый CI останавливается до native fan-out. Отдельный guarded write job может создать один форматирующий дочерний commit только в собственной PR-ветке (не main/base/fork), с exact-head lease и явным workflow_dispatch нового SHA. Перед push требуется ancestry текущего PR base; новая матрица проверяет чистый commit целиком; автоматический dispatch не запускает release builds и не чинит себя повторно. Ошибки синтаксиса, инструментов, конфликт ветки или запрещённый diff остаются красными. Никаких overlays, post-green commits или ослабления ci-gate.
- Базовые команды внутри CI jobs: `cargo test --workspace --all-targets --locked`, `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`.
- CI сначала проверяет спецификацию и тесты, затем lint/build; кэш cargo/target через `Swatinem/rust-cache`; Windows проверяется нативно.
- **Оптимизированный CI — постоянное требование проекта, а не разовая задача.** При изменении workflows, зависимостей, тестов и структуры workspace сохраняй и по возможности улучшай время до результата, суммарные runner-minutes, эффективность кэша и потребление ресурсов. Устраняй дублирующие сборки, установки, проверки и ненужные повторные запуски; сохраняй fail-fast preflight, корректное кэширование, разумный параллелизм, безопасную отмену устаревших прогонов и доказуемо корректные fast paths.
- Для CI-оптимизаций измеряй сопоставимые GitHub Actions runs до/после (с учётом ОС, cold/warm cache, состава jobs и critical path), фиксируй существенные изменения и регрессии в `docs/CI_PERFORMANCE.md` / `docs/TESTING_CI.md`. Не обещай экономию без измерений; не допускай необоснованного ухудшения времени и стоимости CI.
- **Экономь на количестве запусков и дублировании, а не на покрытии.** Не удаляй обязательные native Linux/Windows, security, BBR, fingerprint, F-14 cross-host, smoke/E2E, fuzz или иные release gates ради скорости. Docs-only fast path допустим лишь при доказанном безопасном diff; неизвестные/смешанные изменения требуют полной матрицы. Сохраняй CI-only и fail-closed семантику итогового `ci-gate`; запрещены skip обязательных jobs, подмена native E2E моками и ложный green.
- Никакой микрооптимизации без замеров и регрессий в тестах. Производительность в `docs/TESTING_CI.md` — измеряется на одинаковых условиях.

- Production CLI dispatch is exhaustive: parsing is side-effect-free, invalid arguments fail before runtime, unsupported platforms refuse explicitly. Both server and client H2/H3 runtimes, typed TOML and the TUI are integrated; retain the compiled binary's positive and negative CI regressions.

## Definition of Done (для каждого среза)

- [ ] Есть автоматизированный позитивный и негативный тест; пограничные значения покрыты.
- [ ] Код соответствует спецификации; отклонения объяснены ADR, а не спрятаны.
- [ ] Проведены проверки безопасности (аутентификация, таймауты, валидация, файловые права).
- [ ] Тексты ошибок, UX и TOML обновлены, когда требуется.
- [ ] `cargo test`, `fmt`, `clippy` и целевые платформы проходят в CI; итоговый `ci-gate` успешен для точного head SHA. Нет ручных шагов тестирования.
- [ ] Нереализованные функции не доступны как работающие и не заявлены в README.

## Запрет на «фиктивную готовность»

Нельзя закрывать задачу заглушкой, возвращающей успех, snapshot-тестом без проверки поведения, ложным счётчиком скорости, «браузерной совместимостью» через единственный заголовок или fallback при любом исключении.

**Сначала минимальный защищённый TCP-туннель с тестами. Перед объявлением MVP готовым обязательно завершить P0 BBR, REALITY-подобный F-18, измеренную защиту TLS-in-TLS F-19 и проверенный browser-like fingerprint профиль; ни один из этапов нельзя выдавать за уже реализованный.**
