# M3.3: QUIC BBR vs CUBIC, обязательный исследовательский CI

Тестовый код: `spikes/m0_1/tests/quic_congestion_comparison.rs`. Не входит в production binary, не меняет BBR на CUBIC в Theia. Запускается исключительно GitHub Actions `m3-3-bbr-comparison` на Linux и Windows; итоговый `ci-gate` требует успеха обоих исполнений. Сырые данные сохраняются как CSV artifacts `m3-3-quic-comparison-Linux` и `...-Windows`, проверяются `tests/benchmark/check_bbr_comparison.py`.

## Протокол эксперимента

Каждый прогон проверяет реальный UDP/QUIC/TLS 1.3 с обычной проверкой сертификата localhost, отсутствие 0-RTT, фактически активный класс BBR или CUBIC на обоих участниках. Один сервер отправляет **512 КиБ** в одном QUIC потоке; клиент проверяет *каждый байт*, затем возвращает подтверждение. Измеряется время от начала отправки до подтверждения (включает задержку приложения, перепередачи и синхронизацию runner), оценка полезной скорости Мбит/с и Quinn PathStats: RTT, отправленные и потерянные пакеты, congestion events.

Одинаковые параметры для BBR и CUBIC: четыре режима, по два последовательных повторения каждого; контроллеры чередуются внутри режима:
1. Базовая localhost сеть, без искусственных потерь и задержек.
2. Отбрасывание каждой двадцатой *попытки передачи исходящей UDP датаграммы* после TLS.
3. Дополнительная односторонняя задержка 8 мс с детерминированным джиттером до 8 мс.
4. Совместно потеря каждой двадцатой попытки и задержка с джиттером.

Тестовая `AsyncUdpSocket`-обёртка отключает UDP GSO, ограничивает число отложенных датаграмм (**2048**) и записывает все параметры инъекции. Гарантируется доставка 512 КиБ байт-в-байт для завершённых прогонов, реальная активность требуемого контроллера, наличие инъекции в ненулевых режимах и числовая корректность CSV. Неизвестные режимы, пропущенные повторы и повреждённые данные обрывают CI.

## Границы доказательств

Это *синтетический локальный эксперимент*, а не эмуляция реального WAN. Время выполнения заданий Tokio, масштабирование CPU и реальное планирование пакетов у runner неконтролируемы; `try_send` означает попытку отправки, а не успешный QUIC packet. Односторонняя задержка в задаче Tokio и джиттер не эквивалентны гарантированному network RTT или ограниченной скорости канала. Два повтора недостаточны для статистической значимости. Вывод checker намеренно **не** устанавливает победителя, не утверждает преимущество BBR над CUBIC, не меняет production настройки и не снимает релизный блокер F-11.

Для закрытия F-11 нужны выделенные воспроизводимые benchmark runners с контролируемой пропускной способностью, RTT, потерями и джиттером, независимыми сериями (p50/p95 и интервалы), pacing/fairness при конкурирующих потоках, CPU/peak RSS, сопоставление с baseline, отчёт по обоим ОС и заранее определённые критерии приемки. Всё выполняется исключительно CI; ручные измерения не принимаются.
