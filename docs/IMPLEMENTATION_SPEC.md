# Спецификация реализации Theia

**Версия спецификации:** 0.3 (проектная)  
**Статус:** normative target, не описание текущего кода.  
**Референсы по идее продукта:** удалённая серверная панель на Linux (по смыслу 3x-ui) и самостоятельный Windows/Linux-клиент с импортом подключений (по смыслу NekoBox/v2rayN/Clash Verge). Обе роли входят в один исполняемый файл для соответствующей ОС. Совместимость с их wire-протоколами **не требуется**.

## 1. Назначение

Theia — self-hosted прокси-система на Rust с одним бинарником, двумя логическими ролями, локальным TUI и TOML вместо БД. Сервер обслуживает настроенные inbound-точки; клиент принимает приложения через локальный прокси и направляет разрешённые запросы к выбранному inbound посредством SmartTheia. Продукт ориентирован на небольшие персональные и управляемые развёртывания, а не на мультиарендную SaaS-платформу.

### 1.1 Словарь

- **Inbound:** публичная точка сервера с адресами UDP/TCP, TLS-сертификатом, набором пользователей и политикой.
- **Profile:** клиентский набор адреса сервера, секрета, транспорта и локальных proxy-настроек.
- **SmartTheia:** версия прикладного frame-протокола поверх HTTP/3 или HTTP/2 (см. protocol doc).
- **Fallback:** выбор альтернативного транспорта для **нового** подключения; не миграция живого TCP-потока.
- **System proxy:** пользовательские системные HTTP(S)-proxy параметры Windows, не TUN и не перехват всего трафика.
- **REALITY-подобный SmartTheia:** будущий отдельный защищённый профиль с проверяемой криптографической идентичностью сервера и согласованной внешней TLS/HTTP-мимикрией; не VLESS/XTLS REALITY wire.
- **TLS-in-TLS:** распознаваемый по статистике внешнего потока паттерн вложенных TLS-сессий приложений внутри TLS/QUIC туннеля. Это не ошибка TLS-криптографии.

### 1.2 Платформы

- Server: Linux x86_64 (минимальный релиз). Другое Linux/arm64 — последующая проверка.
- Client: Windows 10/11 x86_64 (минимальный релиз) + Linux x86_64 (удобен для тестов).
- UI: локальный терминал; сервер может работать без TUI как служба.
- Оба режима входят **в один бинарник для каждой целевой ОС**. Один и тот же файл не обязан исполняться на разных ОС.

**F-14 (обновление 0.2) теперь P0:** единый бинарник содержит **две самостоятельные роли**: серверная TUI на удалённом Linux-сервере (возможен SSH, сервер работает headless) и клиентская TUI на локальной Windows/Linux-машине (управляет импортированными профилями и локальным proxy). Доступ к серверному управлению с клиентской панели по сети в MVP не включён; ссылки подключений являются переносимыми данными, а не каналом администрирования.

**P0 = минимальный публичный MVP.** P1 = после доказанной работы базового туннеля. «Всё в одном» не означает все функции в одном коммите.

## 3. Сценарии и критерии приёмки

### Сценарий A: первый запуск сервера
1. Оператор выполняет `theia tui --role server` и видит список inbound, диагностическое состояние и предупреждение об отсутствующих сертификатах.
2. Создаёт inbound, назначает ID, UDP/TCP bind, доменное имя, TLS-файлы, пользователя с 256-битным случайным токеном **и явно включает его ID в `allowed_user_ids` данного inbound**.
3. TUI предлагает сохранить TOML атомарно и применить через локальный IPC. Не применяет невалидные файлы.
4. `theia server run --config ...` стартует headless, логирует bind и число inbound, но не ключи/токены.
5. Если порт занят или TLS-файл не читается, оператор получает понятный отказ, прежняя активная конфигурация остаётся.

### Сценарий B: Windows-клиент
1. Пользователь добавляет профиль и секрет в TUI. Пароль/токен по умолчанию скрыт.
2. `theia client run` запускает только loopback listeners.
3. Local proxy отображается как «Слушает», но не «Подключён». При первом HTTP CONNECT/SOCKS5 клиент ждёт `OPEN_OK`; только тогда возвращает приложению успешный proxy-ответ. Для домена DNS выполняет сервер; тест туннеля использует явно разрешённую цель.
4. Включение системного прокси потребует отдельного подтверждения. При выходе/сбое предыдущее состояние восстанавливается с проверкой собственности настроек.
5. Приложения, игнорирующие системный прокси, **не обязаны** проходить через Theia (TUN вне MVP).

### Сценарий D: выдача подключения и импорт (F-14, P0)
1. Серверный оператор по SSH или в локальной TUI выбирает inbound и создаёт нового пользователя с CSPRNG-случайным 32-байтным токеном; активный пользователь явно включается в allowed_user_ids **этого** inbound. До успешной проверки и записи конфигурации приглашение не считается рабочим.
2. По умолчанию можно экспортировать **публичный профиль без токена**. Для одноразовой выдачи полного подключения оператор явно подтверждает секретный экспорт при **создании или ротации** токена: URI theia://v1/... или защищённый файл. Хеш, уже сохранённый в серверном TOML, **не может восстановить** токен. Не показывать токен повторно автоматически.
3. На клиентском компьютере пользователь выбирает Импорт → Вставить ссылку / Выбрать файл; получает безопасный preview (адрес, TLS/SNI, транспорт, имя), подтверждает новый профиль. Импорт не загружает произвольный URL и не изменяет системный прокси; неизвестная схема/версия/ключи, невалидный токен, конфликт ID и непроверенный TLS trust блокируют подключение. Секрет помещается отдельно в защищённый файл (Unix 0600, Windows per-user ACL) либо явно назначенную переменную среды, а TOML хранит только file:/env: ссылку.
4. Выбор профиля, запуск локального SOCKS5/CONNECT, подключение и включение Windows system proxy — **отдельные действия**; статус «подключён» возможен только после авторизованного транспортного подтверждения. Отзыв и ротация токена не восстанавливают старое приглашение.
5. Автоматический Linux-server/Windows-client E2E создаёт токен, выдаёт полное подключение, импортирует его и проверяет OPEN_OK через HTTP CONNECT/SOCKS5. Неверный grant, удалённый/отключённый пользователь, повреждённый URI, неверная CA и конфликт сохранения — отрицательные CI-тесты.

### Сценарий E: подбор и применение REALITY-подобного профиля (F-18, P0)
1. Оператор на удалённом сервере открывает «Inbound → Защита от DPI → Проверить и подобрать», выбирает список разрешённых IP/доменов. Пассивная оценка не отправляет сетевых проб; активные TLS/HTTP probes запускаются только после отдельного согласия и только для собственных/разрешённых целей, с жёсткими лимитами. Не сканировать массово чужие диапазоны.
2. TUI показывает список с score 0–100 (эвристика, **не вероятность обхода DPI**), измеренными TLS1.3/ALPN/SNI/cert/fingerprint признаками, временем/сетевым контекстом, confidence и объяснением выбора. Отсутствие доказательства не трактуется как пригодность.
3. Второе основное действие «Применить» показывает typed preview, сохраняет валидный конфиг и только через защищённый IPC транзакционно активирует профиль с rollback; не выдаёт токен, не открывает OS proxy и не объявляет «Активно» при ошибке. В клиент он передаётся только через будущий версионированный формат F-14, не старый theia://v1.
4. Неверный ключ, ошибочный TLS/SNI, неподдерживаемый режим/H3 или auth/protocol mismatch — отказ, не silent fallback. Пока нет настоящего backend и CI, функциональность остаётся нереализованной.

### Сценарий F: TLS-in-TLS (F-19, P0)
1. В изолированных Linux/Windows E2E тестах обычный HTTPS проходит внутри SmartTheia H2/H3: сравниваются обычный браузерный HTTPS, Theia без защиты и Theia с подтверждённым flow-shaping.
2. Independent classifier измеряет TPR при FPR ≤1% на заранее выделенном наборе, confidence и дельту; отдельно проверяются размер/время/направление и throughput/latency/CPU/RSS. Пороги приёмки утверждаются **до** измерения релизной выборки.
3. Защита не декодирует внутренний TLS, не меняет байты, не делает видимость OPEN_OK раньше реального соединения и не создаёт бесконечные очереди. В required режиме отсутствие поддержки отказывает, а не тихо выключает защиту.

### Сценарий C: транспортный выбор
- UDP доступен: HTTP/3 выполняет handshake и переносит TCP-поток, HTTP/2 не нужен.
- UDP заблокирован, TCP 443 доступен: по истечении ограниченного таймаута пробуется HTTP/2; соединение работает.
- Сертификат неверен, токен отозван, SmartTheia version несовместима: **нет fallback** с целью обхода ошибки; показать конкретную диагностическую категорию.
- После смены сети и TTL наблюдений повторить QUIC-probe для новых соединений; не обрывать активные.
- Выбранный транспорт виден в диагностике без публикации чувствительных метаданных.

## 4. Нефункциональные требования

**Безопасность:** TLS 1.3 и строгая верификация, crypto из проверенных библиотек, ограничение ресурсов, секреты без логирования, минимум привилегий. Сервер не должен превращаться в открытый relay; по умолчанию private ranges заблокированы, DNS rebinding учитывается после resolution.

**Надёжность:** timeout для подключения/handshake/чтения, graceful shutdown, ограниченные очереди и backpressure, отмена задач, отсутствие бесконечного ретрая, ясная ошибка при неуспехе обоих транспортов.

**Совместимость:** стабильная wire version и schema_version. Несовместимые изменения требуют нового major protocol/schema и тестов миграции.

**Производительность:** измерять p50/p95 latency, throughput, CPU, RSS, число соединений, долю fallback и ошибки. Не вводить произвольные утверждения «быстрее Xray» без одинакового benchmark. Цель — умеренный footprint и простая эксплуатация, измерения обязательны до релиза.

**DPI:** угрозы включают анализ ALPN/SNI, QUIC/TLS fingerprints, тайминги, длины пакетов, HTTP/2 SETTINGS/HTTP/3 поведение, active probing, TLS-in-TLS и блокировку UDP. P0 требует измеренного browser-like профиля, но не обещает неотличимость на всех уровнях. Если выбранный TLS backend не позволяет изменить требуемые компоненты ClientHello, это **архитектурный блокер**, а не основание заменить uTLS одним User-Agent. Проверки и ограничения указаны в протоколе.

## 5. Явно вне объёма MVP

Веб-панель, БД, распределённая координация, чужие VLESS/TUIC wire-сервера, обещания невидимости/обхода любых блокировок, анонимизирующая сеть, автоматический выпуск сертификатов, mesh/P2P, TUN/VPN, UDP relay до P1, межпользовательские ACL с SaaS-правами.

## 6. Релизное определение «готово»

Все P0 (включая REALITY-подобный F-18 и мастер подбора, измеренные anti-TLS-in-TLS меры F-19, end-to-end выдачу/импорт приглашений F-14, BBR и измеренный browser-like профиль) проходят на Linux server и Windows client **реальным сетевым E2E**, протокол и TOML имеют версионные тесты, Windows system proxy подтверждён автоматическим CI smoke/recovery тестом на изолированном временном профиле/VM, security review не имеет блокирующих результатов, CI зелёный. До этого статус — experimental/unreleased.

Все критерии тестирования и приёмки подтверждаются автоматическими CI jobs; обязательные ручные тесты не допускаются. Нереализованный автоматический сценарий является release blocker, а не поводом делегировать проверку пользователю.

**Исследовательский статус M3.5a0:** TLS1.3/H2 и QUIC/H3 exporter channel binding тестируется только на изолированных loopback fixtures. Само по себе это не является F-18 REALITY-подобным профилем или F-19 TLS-in-TLS защитой. До нового криптографического ADR, раздельных first-flight сетевых E2E и независимого security review статус P0 остаётся открытым. См. docs/adr/0021-m3-5a-rustls-quic-auth-feasibility.md.
