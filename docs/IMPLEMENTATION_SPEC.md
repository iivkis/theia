# Спецификация реализации Theia

**Версия спецификации:** 0.1 (проектная)  
**Статус:** normative target, не описание текущего кода.  
**Референсы по идее продукта:** Xray + 3x-ui, sing-box + s-ui. Совместимость с их wire-протоколами **не требуется**.

## 1. Назначение

Theia — self-hosted прокси-система на Rust с одним бинарником, двумя логическими ролями, локальным TUI и TOML вместо БД. Сервер обслуживает настроенные inbound-точки; клиент принимает приложения через локальный прокси и направляет разрешённые запросы к выбранному inbound посредством SmartTheia. Продукт ориентирован на небольшие персональные и управляемые развёртывания, а не на мультиарендную SaaS-платформу.

### 1.1 Словарь

- **Inbound:** публичная точка сервера с адресами UDP/TCP, TLS-сертификатом, набором пользователей и политикой.
- **Profile:** клиентский набор адреса сервера, секрета, транспорта и локальных proxy-настроек.
- **SmartTheia:** версия прикладного frame-протокола поверх HTTP/3 или HTTP/2 (см. protocol doc).
- **Fallback:** выбор альтернативного транспорта для **нового** подключения; не миграция живого TCP-потока.
- **System proxy:** пользовательские системные HTTP(S)-proxy параметры Windows, не TUN и не перехват всего трафика.

### 1.2 Платформы

- Server: Linux x86_64 (минимальный релиз). Другое Linux/arm64 — последующая проверка.
- Client: Windows 10/11 x86_64 (минимальный релиз) + Linux x86_64 (удобен для тестов).
- UI: локальный терминал; сервер может работать без TUI как служба.
- Оба режима входят **в один бинарник для каждой целевой ОС**. Один и тот же файл не обязан исполняться на разных ОС.

## 2. Функциональные требования

| ID | Приоритет | Требование и наблюдаемое поведение |
| --- | --- | --- |
| F-01 | P0 | `theia tui` предлагает две панели «Для сервера» / «Для клиента», конфигурации независимы. |
| F-02 | P0 | Сервер запускается headless, слушает TCP+UDP на одном числовом порту при разных transport sockets, может иметь несколько inbound с уникальными ID и непересекающимися bind-адресами. |
| F-03 | P0 | Клиент поднимает loopback HTTP CONNECT и SOCKS5, не открывая незащищённый публичный proxy. |
| F-04 | P0 | Клиент в режиме auto пытается HTTP/3 over QUIC, затем HTTP/2 over TLS при подтверждённой сетевой недоступности QUIC. |
| F-05 | P0 | Сервер и клиент используют один SmartTheia v1 frame parser и проверку протокольных состояний. |
| F-06 | P0 | Проверяется TLS hostname/chain; bearer-токен сопоставляется только с явно назначенными данному inbound пользователями; разрешённые цели проверяются после DNS. Private/link-local/loopback заблокированы по умолчанию. |
| F-07 | P0 | Клиент Windows включает системный пользовательский HTTP(S) proxy **по явному действию**, сохраняет предыдущее состояние и восстанавливает его без затирания чужих изменений. |
| F-08 | P0 | Все настройки в версионированных TOML; проверка, сообщения об ошибках с путем поля и атомарная запись; без SQL/Redis. |
| F-09 | P0 | TUI поддерживает клавиатуру, состояние unsaved changes, валидацию до применения, подтверждение опасных операций, восстановление терминала после ошибки. |
| F-10 | P0 | Headless сервис не зависит от открытого терминала; диагностика/управление локально через защищённый IPC. |
| F-11 | P0 | QUIC BBR в **обоих передающих направлениях** по проверенному API выбранного QUIC стека; функциональный тест выбора алгоритма и тесты в условиях потерь. При неподдерживаемой реализации MVP блокируется. |
| F-12 | P1 | UDP relay с объявлением capability, без ложного обещания поддержки в MVP. |
| F-13 | P0 | Как минимум один **реально реализованный и измеренный** именованный browser-like профиль TLS/HTTP fingerprint (аналог настраиваемости uTLS), доступный Windows/Linux. Для H2 структурный эталон ClientHello может воспроизводимо генерироваться **пинненной Go uTLS** (без захватов живого браузера). Для H3 нужен отдельный QUIC-совместимый эталон; тесты реального сетевого поведения **Theia** и отчёт о расхождениях обязательны. Наличие Go-генератора эталона без рабочего TLS/QUIC backend не выполняет F-13; без обещания DPI-невидимости. |
| F-14 | P1 | Экспорт/импорт клиентского профиля без раскрытия секрета по умолчанию; ручная установка ключа при импорте. |
| F-15 | P2 | TUN, маршрутизация по доменам/приложениям, продвинутая статистика и mobile. |
| F-16 | P0 | HTTP CONNECT возвращает `200`, а SOCKS5 — success **только после** SmartTheia `OPEN_OK`; при ошибке возвращается корректный отказ, без ложного туннеля. |
| F-17 | P0 | Доменный CONNECT/SOCKS5 передаёт hostname серверу без локального DNS lookup; сервер выполняет DNS, IP ACL и dial закреплённого разрешённого адреса. |

**P0 = минимальный публичный MVP.** P1 = после доказанной работы базового туннеля. «Всё в одном» не означает все функции в одном коммите.

## 3. Сценарии и критерии приёмки

### Сценарий A: первый запуск сервера
1. Оператор выполняет `theia tui --role server` и видит список inbound, диагностическое состояние и предупреждение об отсутствующих сертификатах.
2. Создаёт inbound, назначает ID, UDP/TCP bind, доменное имя, TLS-файлы, пользователя с 256-битным случайным токеном **и явно включает его ID в `allowed_user_ids` данного inbound**.
3. TUI предлагает сохранить TOML атомарно и применить через локальный IPC. Не применяет невалидные файлы.
4. `theia server run --config ...` стартует headless, логирует bind и число inbound, но не ключи/токены.
5. Если порт занят или TLS-файл не читается, оператор получает понятный отказ, прежняя активная конфигурация остаётся.

### Сценарий B: Windows-клиент
1. Пользователь добавляет профиль и секрет в TUI. Пароль/токен по умолчанию скрыт.
2. `theia client run` запускает только loopback listeners.
3. Local proxy отображается как «Слушает», но не «Подключён». При первом HTTP CONNECT/SOCKS5 клиент ждёт `OPEN_OK`; только тогда возвращает приложению успешный proxy-ответ. Для домена DNS выполняет сервер; тест туннеля использует явно разрешённую цель.
4. Включение системного прокси потребует отдельного подтверждения. При выходе/сбое предыдущее состояние восстанавливается с проверкой собственности настроек.
5. Приложения, игнорирующие системный прокси, **не обязаны** проходить через Theia (TUN вне MVP).

### Сценарий C: транспортный выбор
- UDP доступен: HTTP/3 выполняет handshake и переносит TCP-поток, HTTP/2 не нужен.
- UDP заблокирован, TCP 443 доступен: по истечении ограниченного таймаута пробуется HTTP/2; соединение работает.
- Сертификат неверен, токен отозван, SmartTheia version несовместима: **нет fallback** с целью обхода ошибки; показать конкретную диагностическую категорию.
- После смены сети и TTL наблюдений повторить QUIC-probe для новых соединений; не обрывать активные.
- Выбранный транспорт виден в диагностике без публикации чувствительных метаданных.

## 4. Нефункциональные требования

**Безопасность:** TLS 1.3 и строгая верификация, crypto из проверенных библиотек, ограничение ресурсов, секреты без логирования, минимум привилегий. Сервер не должен превращаться в открытый relay; по умолчанию private ranges заблокированы, DNS rebinding учитывается после resolution.

**Надёжность:** timeout для подключения/handshake/чтения, graceful shutdown, ограниченные очереди и backpressure, отмена задач, отсутствие бесконечного ретрая, ясная ошибка при неуспехе обоих транспортов.

**Совместимость:** стабильная wire version и schema_version. Несовместимые изменения требуют нового major protocol/schema и тестов миграции.

**Производительность:** измерять p50/p95 latency, throughput, CPU, RSS, число соединений, долю fallback и ошибки. Не вводить произвольные утверждения «быстрее Xray» без одинакового benchmark. Цель — умеренный footprint и простая эксплуатация, измерения обязательны до релиза.

**DPI:** угрозы включают анализ ALPN/SNI, QUIC/TLS fingerprints, тайминги, длины пакетов, HTTP/2 SETTINGS/HTTP/3 поведение, active probing и блокировку UDP. P0 требует измеренного browser-like профиля, но не обещает неотличимость на всех уровнях. Если выбранный TLS backend не позволяет изменить требуемые компоненты ClientHello, это **архитектурный блокер**, а не основание заменить uTLS одним User-Agent. Проверки и ограничения указаны в протоколе.

## 5. Явно вне объёма MVP

Веб-панель, БД, распределённая координация, чужие VLESS/TUIC wire-сервера, обещания невидимости/обхода любых блокировок, анонимизирующая сеть, автоматический выпуск сертификатов, mesh/P2P, TUN/VPN, UDP relay до P1, межпользовательские ACL с SaaS-правами.

## 6. Релизное определение «готово»

Все P0 (включая BBR и измеренный browser-like профиль) проходят на Linux server и Windows client **реальным сетевым E2E**, протокол и TOML имеют версионные тесты, Windows system proxy подтверждён ручным smoke-тестом на чистом профиле, security review не имеет блокирующих результатов, CI зелёный. До этого статус — experimental/unreleased.
