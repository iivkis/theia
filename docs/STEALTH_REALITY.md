# F-18/F-19: REALITY-подобный режим, подбор мимикрии и защита TLS-in-TLS

**Статус (2026-11-24):** обязательная целевая спецификация P0. **Статус полноценного F-18/F-19:** не реализовано. **REALITY-подобный защищённый режим и измеренная anti-TLS-in-TLS защита не реализованы.** Отдельные контролируемые эксперименты уже доступны: offline-кандидаты и эвристический evidence score, opt-in точечные H2/H3 TLS checks, закреплённый после согласия DNS. Это **не** полноценный автоматический сканер, не доказательство прав на IP и не мастер Apply. Состав выполненных срезов: [STATUS.md](STATUS.md); для новых crypto/wire/TOML версий требуются ADR и CI E2E.

## M3.5a0 — криптографическая feasibility-проверка (исследование, не REALITY)

В отдельном PR добавлена исследовательская матрица **обычных** реальных соединений TLS1.3/TCP с ALPN h2 и QUIC/TLS1.3 с ALPN h3; у обоих транспортов используются экспортёры ключевого материала из уже **проверенных** TLS сессий, с доменным разделением LABEL/CONTEXT. Проверяются несовпадающий CA, отказ новым полям security mode в TOML v1 и запрет объявления smart-reality-v1 в theia://v1. Тестовый файл: crates/theia/tests/reality_security_feasibility.rs; решение и пределы доказанного: docs/adr/0021-m3-5a-rustls-quic-auth-feasibility.md.

**Вывод:** H2 и H3 обладают примитивом channel binding, но он **не** заменяет REALITY-модифицированное TLS-рукопожатие, pinned server identity, replay/active-probing defense или согласованный внешний QUIC/HTTP fingerprint. Из-за этого **F-18/F-19 остаются открытыми P0**. Следующий M3.5a1 — проектирование/audit протокола идентичности и real first-flight modified handshake feasibility; M3.5a2 — отдельная возможность QUIC/H3. Нельзя выставлять новый tls_profile или разрешать insecure verifier на основании exporter tests.

## M3.5a1 — test-only независимый server identity proof (проект на crypto review)

Исследовательский срез [ADR-0059](adr/0059-f18-m3-5a1-identity-research-lab.md) отделяет cryptographic server identity от обычного CA-проверенного TLS. Через `ring` Ed25519 проверяется строго подписанный typed transcript: transport H2/H3, DNS/SNI/port, fresh 32-byte CSPRNG challenge/nonce, миллисекундный freshness и **экспортёр конкретного уже проверенного TLS-канала**. Отрицательные тесты не принимают неправильный pin, изменённый transport/name/nonce/exporter, повтор, истёкший proof или переполненный bounded replay cache. Отдельный loopback TLS1.3/H2 test действительно передаёт challenge/proof поверх защищённой сессии. Существующий H3/QUIC exporter test остаётся отдельным, и H3 identity flight **ещё не реализован**.

Этот код существует **только в CI integration tests**, не доступен из production server/client, не меняет TOML/invite v1 и **не является** REALITY-подобным режимом, реальным on-wire contract, anti-probing или TLS camouflage. Подпись после обычного TLS не скрывает первый TLS/QUIC handshake. M3.5a2 QUIC first-flight и независимый security review остаются блокирующими перед любым user-facing mode. Нельзя считать F-18 выполненным по этим тестам.

## M3.5a2 — реальный QUIC Initial witness + HTTP/3 DATA proof (research-only)

[ADR-0060](adr/0060-f18-m3-5a2-quic-initial-h3-research.md) и `crates/theia/tests/f18_h3_first_flight.rs` добавляют **нативный Linux/Windows CI-only эксперимент**. Настоящий Quinn client отправляет Initial через строго локальный bounded UDP observer, который разбирает **только открытые QUIC v1 long-header поля**: тип пакета, версию, длины CID, token length, packet/datagram length и обязательное QUIC-пополнение до ≥1200 байт. Не сохраняются байты пакетов, реальные CID, секреты, TLS ClientHello или адреса пользователя. В том же controlled loopback используется строгий QUIC/TLS1.3/CA/SAN/SNI/ALPN=h3 и настоящий **HTTP/3 POST DATA** для challenge/Ed25519-pinned identity response с real post-handshake exporter. Неправильный публичный ключ, H2↔H3 подмена и replay отвергаются test-only verifier; malformed/short/non-v1 Initial не выдаются за доказательство.

**Не подтверждено:** расшифрованный QUIC Initial CRYPTO и полный on-wire TLS ClientHello/transport parameters, воспроизведение browser H3 fingerprint, modified REALITY first flight, early server-side client authentication/anti-probing, replays после перезапуска, полноценный F-18 security mode или F-19 shaping. HTTP 200 в исследовательском эксперименте **не** SmartTheia OPEN_OK. Это исследовательский тест, а не новый runtime security mode. Отдельное доказательство совместимости modification backend и независимый crypto review остаются блокирующими.

## M3.5b1 — чистый offline planner кандидатов (реализован частично)

Файл `crates/theia/src/camouflage_discovery.rs`, integration tests `crates/theia/tests/camouflage_discovery.rs`, ADR-0022. Код в текущем *едином* Rust binary (library module) без новых зависимостей, не имеет ни socket/DNS/HTTP/TLS вызовов, ни CLI/TUI команды:

- `build_plan(ServerSnapshot, approved CIDRs)` запускается только по **уже предоставленным** данным интерфейсов/egress; будущий OS collector пока отсутствует. Каталог из 14 доменов (`google.com`, `samsung.com`, `amd.com`, и т.д.) включается всегда без ручного seed; адреса интерфейсов добавляются только если выглядят публично-маршрутизируемыми. Неизвестный/NAT egress показывает предупреждение.
- Предположительно определённый provider prefix **не** позволяет перечислить IP. Только явно переданный caller-ом approval и совпадение с реально указанным публичным *локальным интерфейсом* допускают построение списка для IPv4 CIDR `/24` либо уже. Это **не** сама проверка права владеть подсетью: будущий TUI/permission collector отвечает за явную авторизацию. IPv6 `/64` не перечисляется; reserved/private/CGNAT/documentation адреса консервативно исключаются. В M3.5b2b0 добавлена fail-closed проверка: approved IPv4 CIDR не должен выходить за наблюдаемую маску локального интерфейса (`/32` не превращается в `/24`; неизвестный `/0` и неверный префикс отвергаются). Это защита offline candidate planner, а не доказательство ownership: отдельные маршрутизируемые диапазоны потребуют самостоятельной проверенной provenance и согласия в будущей версии. Очередь ограничена `MAX_CANDIDATES=256` с dedup и диагностикой усечения.
- `TlsEvidence::suitability(H2|H3)` вычисляет прозрачный **эвристический** score/confidence/блокирующие причины из *внешних проверенных наблюдений*. По умолчанию все поля `Unknown`, score=0, confidence=0, `eligible=false`; ни популярность домена, ни IP не превращаются в реальный TLS certificate/fingerprint proof. Разные ALPN h2/h3 оцениваются независимо. Поле `theia_fingerprint_match` не заполняется этим модулем: F-13 открыто.
- **На этапе M3.5b1** ещё не были реализованы OS interfaces, DNS, TLS handshakes и UI; последующие M3.5b2b и M4.5 добавили ограниченные opt-in проверки. **По-прежнему отсутствуют** полноценные DNS/CT/RDAP reputation pipeline, калиброванный score, законченный двухшаговый Apply, REALITY-like handshake и TLS-in-TLS flow shaping. Модуль возвращает **план кандидатов**, а не результаты сканирования или готовую мимикрию.

## M4.5h — добровольный DNS каталога и dual-transport проверка закреплённых IP

`p→r→d` даёт локальный каталог из 14 известных HTTPS-доменов. Сначала отдельное DNS-согласие Enter/y **на одно имя** (≤5с, ≤64 ответов) и отбрасывание всей выборки при любом небезопасном адресе; выдаются ≤8 уникальных публичных A/AAAA, привязанных в памяти на 60с **с момента завершения DNS lookup** (не с позднего poll TUI); stale/future observation отбрасывается, а worker перепроверяет TTL перед первым TCP/UDP ([ADR-0037](adr/0037-m4-5i-dns-pin-observation-freshness.md)). Затем j/k+Space **вручную** выбирают pinned IP, отдельные Enter/y раскрывают точную пару `IP:443 + DNS SNI` и разрешают строгие TCP/H2 + UDP/QUIC/H3 TLS1.3/PKI/ALPN probes к одним и тем же адресам (без DNS re-resolution). Нет silent scanner всех доменов, DNS rebinding между consent/handshake, HTTP fallback или автоматического Apply. Наличие популярного сайта не доказывает делегированное право активной проверки IP; оно заявляется оператором при втором подтверждении. TLS dual-check не выполняет REALITY server key authentication, HTTP/3 first-flight fingerprint или F-19 TLS-in-TLS protection. [ADR-0036](adr/0036-m4-5h-consented-domain-dns-pinned-dual-tui.md).

## M4.5g — активный серверный TUI пакет отдельных IP из проверенного offline-плана

Подбор больше не ограничен API: **`p→r→b`** показывает собственные локально назначенные IP и, только после отдельного offline-подтверждения `a→CIDR→Enter→y`, потенциальные адреса соседей. Каждый **отдельный** IP надо отметить Space (≤8), Enter раскрывает точные IP:443 и SNI, только затем `y` запускает bounded strict TCP/H2 + UDP/H3 `probe_dual_batch` (2 concurrent, ≤5с/цель, ≤20с весь список), без DNS, браузерных запросов, повторов/авто-fallback. Даже accepted CIDR не доказывает владение или разрешение на тестирование соседей: оператор отвечает за подтверждение прав на каждый конкретный IP. H2/H3 evidence и dual count отображаются в памяти, REALITY/auth/fingerprint/H3 HTTP/anti-TLS-in-TLS/Apply остаются открыты. Нет automatic domain or prefix sweep. [ADR-0035](adr/0035-m4-5g-consented-cidr-dual-batch-tui.md).

## M4.5f — ограниченный source-aware H2+H3 пакет кандидатов

`probe_dual_batch` добавляет неавтоматический API для ≤8 вручную выбранных источников. Отдельное `CandidateConsent::PlannedIp` требует exact public IP одобрения и offline-plan; `PinnedDomain {domain,pinned_ip}` закрепляет выбранное каталоговое имя и SNI к конкретному IP с собственным exact-IP consent. Предпроверка всех целей до первого DNS/UDP/TCP (DNS в этом API вообще нет), ≤2 кандидата одновременно, ≤5s на каждый транспорт, ≤20s общий дедлайн. Каждый IP/SNI должен пройти **два реальных строгих handshake**; один H2 success, UDP silence или отказ CA исключают совместимость с обоими. Нет автоматического перебора соседних IP, CT/DNS discovery, активного пробинга всех 14 популярных доменов, evidence о владении, fingerprint H3, криптографического REALITY режима или Apply. [ADR-0034](adr/0034-m4-5f-source-aware-dual-batch.md).

## M4.5e — обязательный двухтранспортный критерий для будущего REALITY-like подбора

Требование **H2 и H3 одновременно**, проверенные раздельно для **того же pinned IP:443 + SNI**: строгий TCP/TLS1.3/ALPN=h2, строгий UDP/QUIC/TLS1.3/ALPN=h3, цепочка доверенных CA, hostname SAN и expiry, deadline ≤5s, явный exact-IP consent. Текущая серверная TUI `p→t→Enter→y` делает оба **на одном собственном назначенном публичном IP**. Реальное H3 handshake обосновывает H3 score только для QUIC/TLS/ALPN, но не HTTP/3 семантику или browser fingerprint; H2-only, H3-only или ошибка TLS => **dual-compatible НЕТ**. Даже dual TLS success не является готовой REALITY-аутентификацией. IP/CIDR и 14 seed-доменов в текущем offline-каталоге **не сканируются автоматически**; без подтверждённого права на каждый IP/домен, anti-SSRF и лимитов чужие диапазоны недопустимы. [ADR-0033](adr/0033-m4-5e-dual-h2-h3-candidate-gate.md).

## M4.5d — доказательные H2/H3 статусы после strict TLS probe

Успешный строго проверенный TCP/TLS1.3/CA/SAN/SNI/ALPN=h2 ответ `ProbeReport` выводится только после проверки совпадения pinned target IP с `connected_ip`. По существующим seven-field weights это **H2 80/100, confidence 85%, eligible NO** (unknown fingerprint), **H3 score Unknown, confidence 0%, eligible NO** (QUIC/H3 не проверен, H2 TLS доказательства не переносим на H3); это не вероятность обхода DPI и не полноценная F-18/F-19 readiness. Возраст результата отсчитывается монотонно с момента получения TUI, сбрасывается перед новым согласованным probe. Ошибки PKI/ALPN/timeout/mismatched IP дают **score Unknown**, не сулят частичное Verified без evidence. Нет активного domain/CIDR scanner, H3 или REALITY режима, Apply/IPC. [ADR-0032](adr/0032-m4-5d-evidence-score-tui.md).

## M4.5c — источники кандидатов и ограниченный ручной offline CIDR

`p → r` в серверной TUI группирует только наблюдаемые local IP, 14 seed-доменов и вручную введённый IPv4 CIDR. `a → CIDR → Enter` строго проверяет диапазон /24..=/32 через M3.5b1 planner в пределах assigned netmask, с bounded result и каноническим адресом; `y` открывает исключительно **временный** offline-preview с числом дополнительных IP и no eligibility evidence, `n/Esc` отменяют. Всё Unknown => score 0/100/confidence 0, а не шанс DPI bypass. Не доказаны юридические права на CIDR, не авторизовано активное сканирование (особенно соседей), и `ProbeApproval` этим действием НЕ создаётся. Ни DNS, ни внешнего TLS, ни TOML apply. [ADR-0031](adr/0031-m4-5c-candidate-groups-offline-cidr.md).

## M4.5b — отдельное согласие на одиночную TLS/H2 проверку назначенного IP

После пассивного `p` в серверной TUI отдельная `t` панель предлагает до восьми **локальных публичных IP с назначенной валидной маской**, выбор j/k, нуждается в выбранном server inbound SNI. Согласие `Enter/t → y` называет конкретный IP:443, запускает только один уже реализованный M3.5b2b3 TLS1.3/H2 probe с native OS CA, проверенными SAN/SNI/ALPN h2 и deadline ≤5s на фоне. Esc отменяет. Никаких автоматических проб CIDR/seed DNS/ipify claim; private/up/down ограничения fail-closed. Ошибка TLS, timeouts и отсутствие CA показываются как отказ, не verified; даже успешный TLS/H2 ничего не говорит о REALITY, TLS-in-TLS или DPI. Изменений конфигурации/runtime нет. [ADR-0030](adr/0030-m4-5b-explicit-single-ip-h2-tui.md).

## M4.5a — passive-first серверная TUI для IP/подсетей и отдельного согласия ipify

Серверная панель позволяет клавишей `p` просмотреть офлайн-кандидатов и локальные Linux IP/CIDR без внешних запросов. При `i` появляется отдельное предупреждение о передаче публичного IP сервису `https://api64.ipify.org/`; только `y` после него запускает ограниченное 5s DNS + strict TLS1.3 обращение на отдельном рабочем потоке с доверенными CA из ОС, проверенными SNI/ALPN и возможностью отмены Esc. Отказ `n` ничего не отправляет. Windows native local collector пока Unsupported; внешний сервис не вызывается автоматически ни из startup, ни из офлайн-плана. Успешный egress echo не является proof NAT, CIDR ownership, разрешением scanner или DPI обхода. Это **не** мастер выбора IP/domain и Apply, не F-18/F-19, нет активных проб с TUI. [ADR-0029](adr/0029-m4-5a-consented-ip-discovery-panel.md).

## M3.5b2b4 — дефолтный внешний IP-echo через ipify.org (только opt-in)

При явном запросе определения публичного IP стандартным сервисом является **`https://api64.ipify.org/`** (поддерживает IPv4/IPv6, возвращает адрес семейства выбранного TCP-подключения), не `api64.ipify.com`. `observe_default_ipify(RootCertStore, IpifyConsent::Approved)` разрешает фиксированный домен только после согласия; до него нет DNS/TCP, без CA тоже отказ до DNS. Единственный выбранный публичный DNS IP:443 закрепляется для TCP, имя `api64.ipify.org` проверяется через обычный TLS1.3/SAN/CA, http/1.1, no redirect, body/header cap, суммарно до 5 s. Результат является утверждением доверенного по TLS **сервиса**, но не доказывает NAT, владение сетью и не даёт разрешения сканировать диапазон. `default_ipify_request` готовит офлайн шаблон; `observe_public_egress` для custom pinned-host остаётся. В TUI эта опция **не запускается автоматически**, будущий экран согласия должен предупреждать об отправке внешнего IP стороннему сервису. Тесты только через локальные TLS fixture без обращений к ipify. [ADR-0028](adr/0028-m3-5b2b4-default-ipify.md).

## M3.5b2b3 — ограниченные явные TLS/H2 проверки (не сканер)

`camouflage_batch::probe_explicit_batch` может выполнить максимум восемь **явно перечисленных** IP-целей из offline preview, причём публичный IP:443 должен иметь собственное точное `ProbeApproval`. Это не значит, что план разрешает сеть: право проверки/ownership должен отдельно подтвердить оператор. До TCP/TLS вся пачка отклоняется при missing approval, цели вне плана, повторах адресов и превышении лимитов. Модуль использует стандартную strict TLS1.3/CA/SNI/SAN/ALPN=h2 проверку, глобальный предел четырёх concurrent probes и общий batch deadline 20s, возвращает результаты каждой цели в исходном порядке; один отказ не превращается в зелёный общий score. Тесты только на точных loopback fixture. Нет DNS, автоматического сканирования CIDR/seed-доменов, редиректов, H3 или режима REALITY. [ADR-0027](adr/0027-m3-5b2b3-explicit-batch.md).

## M3.5b2b2 — consented HTTPS public-egress witness + offline preview (не scanner)

`camouflage_egress::observe_public_egress` делает **только один** запрос к выбранному оператором pinned public IP:443, с подтверждённым hostname/CA, TLS1.3 и ALPN http/1.1; никаких авто-контактов внешних сервисов. На время/параллелизм/HTTP-ответ/длины устанавливаются строгие лимиты, redirect и private/docs ответ отвергаются. Это реальная сетевая проверка удалённого утверждения о публичном исходящем IP, **не** независимое доказательство принадлежности публичного адреса, NAT, входящей достижимости, внешнего CIDR или права активного тестирования. `camouflage_workflow::build_preview/collect_preview` объединяет достоверные интерфейсы и такое наблюдение со всегда пассивным по умолчанию offline-планом; только отдельно переданный approved CIDR запускает **офлайн перечисление**, но никогда не отправляет probe. `MatchesAssignedAddress/DiffersFromAssignedAddress/Unknown` обозначают сравнение наблюдений, не юридическую или сетевую аттестацию. Только loopback fixture-тесты в CI на Linux/Windows, без внешнего IP-echo. [ADR-0026](adr/0026-m3-5b2b2-consented-egress-preview.md).

Не реализованы automatic egress provider UI, запись/отзыв согласия, bounded active scheduler, подтверждение ownership delegated CIDR, пассивные DNS/CT/RDAP метрики, H3 probe и F-18/F-19.

## M3.5b2b1 — назначенные Linux-интерфейсы и маски (ещё не scanner)

`camouflage_interfaces::collect_assigned_interfaces` читает только локальные UP IPv4/IPv6 интерфейсы и настоящие непрерывные маски через Linux `getifaddrs`, ограничивая количество записей 4096; нулевая/неправильная маска исключается, внешний egress NAT и BGP/RDAP ownership не определяются. `server_snapshot()` выдаёт `egress=None` и пустые inferred-prefixes, не выдаёт операторского approval и не создаёт сетевую очередь самостоятельно. На Windows пока только Unsupported; CI проверяет общий parser и отказ. [ADR-0025](adr/0025-m3-5b2b1-linux-interface-collector.md). F-18/F-19 по-прежнему открыты, активных сетевых проверок нет.

## M3.5b2a — локальное определение маршрута и явный TLS/H2 probe (реализованный экспериментальный library API)

`crates/theia/src/camouflage_probe.rs` содержит **настоящий**, ограниченный по времени TLS 1.3/H2 клиентский handshake через закреплённый `SocketAddr`. Это исследовательский программный API, **не** законченный сканер или видимая пользователю кнопка. Integration tests `crates/theia/tests/camouflage_probe.rs` используют исключительно loopback и временные тестовые CA; публичных доменов и чужих диапазонов в CI никто не сканирует. ADR-0023 фиксирует границы.

- `route_selected_local_ip(destination)` выполняет только системный UDP `connect` без отправки пакета и возвращает локальный source IP выбранного маршрута. **Не** получает netmask/CIDR/egress через NAT, не делает DNS, не подтверждает владение IP, не отправляет probe. Реальный список интерфейсов/префиксы требует последующего OS collector.
- `probe_tls_h2(request, trusted_roots, approval)` **по умолчанию не соединяется** (`ProbeApproval::Denied`). Отдельное `PublicHttpsIp(ip)` даёт доступ только к **ровно этому** публичному IP на TCP 443, а `IsolatedLoopbackFixture(socket)` только к точному loopback endpoint для изолированных тестов. Это не доказательство юридического владения: будущая TUI обязана получить согласие и разрешённый scope до конструирования `PublicHttpsIp`, и не использовать префиксы BGP/RDAP как авторизацию. Нет DNS-переопределения/redirect/перехода на соседние IP, HTTP-запросов или перебора портов.
- Ограничения: максимум **4 одновременных** TLS-probe на процесс через Tokio semaphore, общий handshake deadline `min(request, 5s)` с учётом ожидания слота, TLS **только 1.3**, принудительный ALPN `h2`, обязательные переданные CA trust anchors, обычный строгий rustls hostname/SAN/time/chain verifier. Не используется `insecure_skip_verify`, TOFU или новый криптографический протокол. Неверная CA/SNI/ALPN, пустой trust store, неразрешённый адрес или timeout возвращают отказ без **какого-либо** положительного `TlsEvidence`.
- При успешном handshake только проверенные свойства TLS1.3, chain/SAN/time, TCP reachable и ALPN H2 имеют `Verified`. `alpn_h3` и `theia_fingerprint_match` остаются **Unknown**, поэтому `eligible=false` и score меньше 100. Настоящий TLS handshake **не** подтверждает устойчивость к DPI и не является REALITY-подобной аутентификацией.
- **На этапе M3.5b2a** отсутствовали UI, OS interface collector, batch runner и QUIC/H3 probe; они частично появились в следующих ограниченных срезах. **По-прежнему отсутствуют** полная проверка владения внешними IP, автоматический безопасный scanner/picker с Apply, независимые fingerprint/outer capture measurements, TLS-in-TLS flow shaping, server-key proof и versioned security mode. В README и TUI эти возможности нельзя считать реализованными.

## 1. Цель и модель угроз

Theia должен предлагать отдельно от обычных H2/H3-TLS профилей **REALITY-подобный защищённый режим SmartTheia**, позволяющий согласовать публичный TLS-профиль и наблюдаемое поведение сервиса с реально существующим, стабильным HTTPS-классом трафика. По смыслу функциональность похожа на XTLS REALITY, но **не использует VLESS/REALITY wire protocol и не обещает совместимость с Xray/sing-box**. Нельзя включать заглушку под именем REALITY: без настоящей модели аутентификации сервера и сетевых измерений этот режим не существует.

Противник наблюдает TCP/UDP первые пакеты, TLS ClientHello/ALPN/SNI при отсутствии ECH, QUIC Initial, сертификаты/ошибки, HTTP/2 SETTINGS/HPACK order, HTTP/3 SETTINGS и transport parameters, статистику размеров/направлений/времени/длительности/паузы, корреляцию вложенного TLS (в т.ч. ClientHello приложения внутри внешнего TLS) и активные неавторизованные подключения. Возможны блокировка UDP, анализ TCP fallback, IP/domain reputation и сканирование открытых портов. Противник может отправлять произвольные неавторизованные запросы, но **не знает секретных ключей сервера**. Компрометация клиента/сервера и глобальный всевидящий противник не устраняются.

**Не обещать:** абсолютную невидимость, гарантированный обход DPI/блокировок, «самую лучшую» мимикрию, неотличимость от конкретного чужого сайта, снижение DPI на всех сетях или анонимность. Уровень пригодности кандидата не является метрикой фактической нераспознаваемости туннеля.

## 2. REALITY-подобный режим SmartTheia (F-18 P0)

- Самостоятельный именованный транспортно-защитный профиль, например `smart-reality-v1` как **проектное название**, только после согласования wire contract и способности выбранного TLS/QUIC backend. Не включать это имя в текущее `tls_profile` TOML v1 (валидатор намеренно принимает только `default`), CLI, конфигурационный экспорт `theia://v1/` или обещания README до реальной реализации.
- Совместная **взаимная согласованность** server/client: ключевая пара сервера и проверяемый публичный ключ/идентификатор, доменное имя/целевой TLS-образец, параметры срока действия и ротации, защита от replay и активного probing; CSPRNG и готовая криптографическая библиотека, без собственной криптосхемы. REALITY-подобная аутентификация не может заменяться одной строкой SNI, User-Agent или HTTP-заголовками.
- Подтверждённая идентичность сервера и защита от MITM обязательны. В стандартном H2/H3 остаются строгие hostname/chain/ALPN проверки. В специальном режиме любое **альтернативное доверие к ключу** требует формального threat model, security review и отрицательных тестов подмены/просрочки/replay: запрет `insecure_skip_verify`, TOFU по умолчанию и неявных ослаблений. Нельзя пересылать приватный серверный ключ в приглашении.
- H2/TCP и H3/QUIC имеют **разные** наблюдаемые wire-отпечатки: feasibility для каждого отдельно; H3 НЕ считается поддержанным из-за успешного H2. Никакой silent downgrade между обычным TLS и REALITY-подобным режимом, либо на другой ключ, при auth, PKI, version или policy ошибках; существующий F-04 fallback только при доказанной сетевой недоступности UDP и если обе ветки явно поддерживают один и тот же выбранный security mode.
- Не превращать неавторизованные запросы в открытый relay/SSRF, не перенаправлять произвольные цели без ACL/limiter. Поведение неавторизованного соединения (включая возможный fallback к допустимому camouflage endpoint) сначала проектируется как **bounded, fail-closed, защищённый от probing** и тестируется без утечки версии/идентификаторов/секретов. Никаких произвольных TCP connect к адресу, заданному недоверенным клиентом.
- Встроить в существующую модель одного бинарника, TLS/HTTP библиотеки, TOML, локальный серверный TUI и клиентский TUI, а также F-14 экспорт/импорт. Добавление новых полей/способа доверия требует `schema_version`/формат приглашения v2 и стратегии обратной совместимости. Старый `theia://v1` нельзя молча трактовать как REALITY-подобный.

## 3. Подбор доменов/IP и UX в два основных действия (F-18 P0)

**Мастер на серверной панели:** `Inbound → Защита от DPI → Автоподбор → Применить`. Для уже настроенного/известного набора безопасных кандидатов путь содержит **два основных подтверждённых действия**: (1) «Проверить и подобрать» и (2) «Применить». Просмотр результата, отказ или смена ручных расширенных фильтров не требуют запуска новой настройки. Создание inbound, генерация серверного ключа, выдача клиентского приглашения и отдельное разрешение на активное сетевое сканирование могут требовать дополнительных явных подтверждений безопасности: не скрывать их ради рекламного числа кликов.

- **Автоматическое обнаружение, а не требование ручного списка.** При «Проверить и подобрать» движок сам создаёт две группы кандидатов: **(A) диапазон IP, в котором расположен сервер**, и **(B) встроенный, обновляемый каталог популярных HTTPS-доменов**. Оператору не требуется вручную перечислять ни IP, ни домены. Дополнительные собственные домены/IP разрешены как необязательный расширенный фильтр. Раздельно отмечать `подсеть сервера`, `популярный домен` и `ручной кандидат`, а также источник каждого наблюдения.
- **Выявление серверного диапазона:** определить локальные интерфейсы, адреса, маршруты и назначенные префиксы IPv4/IPv6; выделить публичный адрес интерфейса либо распознанный публичный egress IP с отметкой о NAT/неуверенности. Узнать возможные route/RDAP/BGP-префиксы только как **источник адресных кандидатов**, а не как подтверждение собственности или разрешения на сканирование. Не считать автоматически, что сервер владеет всем /24, /64 или сетью провайдера; не подменять адрес клиента адресом внешнего CDN. При отсутствии достоверного публичного адреса показать статус `не удалось определить` и предложить явное исправление, не выдумывать диапазон. Идентификацию через внешний сервис проводить лишь с согласия оператора, чтобы не раскрывать IP без предупреждения.
- **Обследование соседних IP для поиска HTTPS/TLS:** строить bounded очередь адресов внутри подтверждённого оператором **принадлежащего ему или разрешённого для проверки CIDR**; для чужого/неподтверждённого диапазона ограничиться пассивным обнаружением по опубликованным данным и не делать полное сетевое сканирование соседей. До активных проверок показать CIDR, диапазон и верхний предел адресов/запросов, предоставить cancel. Для IPv6 не перечислять /64: использовать известные DNS/публичные конечные адреса и ограниченные выборки. По умолчанию только порт 443, никакого перебора всех портов. Отсутствие разрешения не должно скрывать результаты пассивного поиска.
- **Встроенный seed-каталог популярных HTTPS-доменов**, как минимум `google.com`, `samsung.com`, `amd.com`, `microsoft.com`, `apple.com`, `amazon.com`, `cloudflare.com`, `github.com`, `mozilla.org`, `wikipedia.org`, `adobe.com`, `intel.com`, `nvidia.com` и `ubuntu.com`; версии, региональные варианты, доменные алиасы, DNS/anycast/CDN и достижимость могут меняться. Каталог является **стартовым списком для оценки, а не списком гарантированно подходящих маскировочных сайтов**; массовую рассылку запросов по нему не выполнять. Пассивно оценивать DNS, доступные CT/public TLS метаданные, HTTPS/SVCB/ALPN hints, если доступны; получение фактически предъявленного сертификата, negotiated ALPN и live TLS версии требует отдельного **активного соединения** с операторским разрешением и rate limits. Для сторонних популярных сайтов не выполнять несанкционированное сканирование диапазонов, HTTP crawling, directory brute force или обход правил.
- **SSL/TLS пригодность:** учитывать успешный handshake TLS1.3, доверенную цепочку CA, совпадение SAN и корректного SNI/DNS, срок действия и renew risk, negotiated `h2`/`h3` в зависимости от ветки, доступность 443/TCP и при наличии 443/UDP, поведение при повторной короткой пробе, ограничения сертификата, latency/стабильность, переносимость TLS/HTTP fingerprint в Theia. Сертификат, который выдаётся **при подключении непосредственно к IP без SNI**, может отличаться от сертификата этого же адреса с DNS SNI, и они оцениваются отдельно. **Сертификат третьей стороны нельзя использовать на сервере Theia без соответствующего приватного ключа/прав**: обнаружение подходящего SSL не означает владения им и не доказывает работоспособную REALITY-подобную мимикрию.
- **Пассивный и активный режимы:** пассивное получение локальных/публичных метаданных и разрешённая оценка работают сразу; активный TLS/HTTP probe запускается только после явного согласия и только для собственных, администрируемых или явно разрешённых целей. Никаких массовых проходов по чужим диапазонам, обхода ACL, неконтролируемого перебора портов или атак. Сам исходный адрес/префикс сервера не является разрешением на сканирование всех его соседей.
- Активный режим: ограниченное число целей/запросов/соединений, concurrency/timeouts/bytes/rate, привязка IP/домена после DNS, no private/loopback/link-local по умолчанию, SSRF protection, отсутствие произвольных redirects, запрет авторизации к удалённым сервисам, cancellation и отчёт об ошибках. Сведения о SNI, TLS version, ALPN h2/h3, времени сертификата, chain/hostname/SAN, стабильности ответов, достижимости/таймаутах и IPv4/IPv6 сопоставляются с поддерживаемым backend. **Не доверять неподтверждённому сертификату ради оценки.**
- Строгие критерии: совместимость с требуемой TLS1.3/ALPN и fingerprint, честно подтверждённая достижимость, соответствие DNS/SNI/cert, поддержка ECH (только если измерена/доступна), стабильность и отсутствие конфликтов TCP/H3 и server-side impersonation traps. Отдельно измерять способность Theia фактически воспроизводить свойства кандидата; просто «сайт открывается» или «сертификат подходит» не означает пригодность для мимикрии.
- Результат: сгруппированный по источникам `серверная подсеть` / `популярные домены` / `ручные` отсортированный список с **баллом пригодности 0–100 (score, только эвристика)**, измеренными компонентами, отметкой `измерено/неизвестно/не поддерживается`, временем и сетью измерения, объяснением/разбивкой причин, погрешностью/уверенностью (confidence), текущими лимитами и явным предупреждением «балл ≠ вероятность обхода DPI». Не ранжировать «нет данных» выше подтверждённого кандидата. Совпадение имени/популярность ресурса без сетевых данных не могут быть единственным критерием. Результаты устаревают и требуют переоценки.
- «Применить» делает **предпросмотр изменений** и транзакционно записывает валидный TOML, при возможности через локальный защищённый IPC с rollback; **не** изменяет системный прокси/Windows client, не создаёт пользователей/ключи без подтверждения и не сообщает «Активно» до применения в runtime. Клиентский профиль или новая ссылка F-14 формируются только после успешной совместной проверки server/client security mode, без публикации приватных ключей или токенов в отчёте сканера.
- Ручная настройка доступна для экспертов; неправильный/просроченный/опасный target/endpoint или отсутствие пригодных кандидатов заканчиваются отказом либо явной рекомендацией оставить стандартный проверяемый TLS, но не ложным «REALITY активен».

## 4. Защита от TLS-in-TLS (F-19 P0)

**TLS-in-TLS** здесь означает наблюдаемые вторичные признаки TLS-сессий приложений внутри зашифрованного TLS/QUIC-туннеля SmartTheia: характерные первые объёмы/последовательности пакетов, направления, интервалы и корреляцию рукопожатий; это **не** ошибка двойного шифрования и не просто наличие двух TLS-соединений. Исследование USENIX Security 2024 показало идентифицируемость некоторых таких туннелей по внешним характеристикам; переносимость результатов на SmartTheia нужно **измерить отдельно**, а не предполагать.

- Ввести отдельную опциональную, явно версионированную **flow-shaping policy** для TCP-stream transport. Кандидаты на feasibility: ограниченное по ресурсам выравнивание размеров chunks, сегментация/коалесцирование данных, контролируемый padding и нормализация/случайная вариация интервалов. Никакого утверждения, что одно лишь padding или перестановка фреймов автоматически скрывает вложенный TLS.
- Сохранять byte-exact TCP поток, корректный FIN/half-close, backpressure, bounded memory/CPU, отсутствие дедлоков и отсутствие задержки `OPEN_OK`; запрет подмены клиентского TLS/SNI/сертификата. Клиентский TLS приложения остаётся **end-to-end** и не декодируется сервером для формирования «маскировки». Классификация внутренних ClientHello по содержимому трафика не должна требоваться, иначе нужна отдельная оценка приватности и безопасности.
- Динамические меры имеют строгие верхние границы overhead (байты/секунду, latency p50/p95/p99, память, CPU), возможность явного `off/optional/required`, контролируемый throughput и явный fallback к безопасному **прежнему** транспортному поведению при отсутствии capability; если защита запрошена как `required`, неподдерживаемый режим **отклоняется**, а не выключается молча.
- Проявления на обоих направлениях и обоих transport branches замеряются **в отдельно зафиксированных реализациях**, с контролем CSPRNG; H2/TCP результат не доказывает H3/QUIC. Непреднамеренные fingerprints от padding, таймингов, HTTP frame alignment и ошибок могут сделать поток более различимым: отрицательный результат не выпускается как успешная защита.
- Независимые оптические метрики: собирать только необходимые **обезличенные** длины, интервалы и направления тестовых пакетов, без TLS private keys, SNI пользователей, токенов, содержимого целей и пользовательских URL. Сравнивать три класса: (A) обычный браузерный TLS/H2 или H3, (B) SmartTheia без мер и (C) SmartTheia с мерами.
- **Приёмка:** воспроизводимый автоматический локальный trace/capture + отдельный классификатор nested TLS/flow statistics, заранее зафиксированные обучающие/тестовые наборы и пороги обнаружения, проверка на отложенных доменах/сетях, TPR при фиксированном FPR ≤1%, доверительные интервалы, baseline и delta между B/C, а также регрессии задержки/throughput/CPU/RSS. Значение FPR/метрика не означает гарантию защиты; окончательные числовые требования к TPR/delta/overhead утверждаются в ADR **до** проведения релизных измерений, не post-hoc по результату. Если профиля с доказанным улучшением нет, F-19 остаётся открытым.

## 5. Совместимость и зависимые требования

- F-13 P0 измеренный browser-like H2/H3 TLS/HTTP профиль — **отдельная зависимость**. Нельзя зачесть F-18/F-19 лишь на основании ClientHello/uTLS эталона, User-Agent или сканирования.
- F-06 auth/grants, F-10 IPC, F-11 BBR, F-14 безопасная выдача/импорт, F-16 OPEN_OK, F-04 QUIC fallback остаются обязательными без ослабления.
- Текущий TOML v1, `theia://v1`, HTTP/2/3 transports и SmartTheia frame v1 **не менялись в исходном проектном ADR и не могут расширяться без нового контракта**. Для новых режимов — последующий ADR с точными versioning, crypto, secret refs, миграцией, совместимостью и negative tests.
- Любая расширенная защита не должна создавать серверный SSRF/fallback proxy и не должна активировать Windows system proxy или remote admin.

## 6. Вертикальный план и release gates

| Этап | Результат |
| --- | --- |
| M3.5a (feasibility) | Threat model, криптографический дизайн REALITY-подобной аутентификации и audit, ограниченный H2/H3 backend spike, измеримые outer fingerprints, no production flag |
| M3.5b (picker) | **Автоматический source discovery:** адрес сервера + проверенный назначенный IPv4/IPv6 CIDR/egress/NAT, отдельная пометка inferred RDAP/BGP prefix без предположения ownership, встроенный каталог google.com/samsung.com/amd.com и других популярных HTTPS-сайтов; пассивный сбор DNS/CT и TLS-кандидатов, явно разрешённый bounded active TLS probe, отдельные сертификаты IP-with/without-SNI, доверие/срок/SAN/ALPN/TLS1.3, объяснимый score. Детерминированные fixtures и Linux/Windows CI; никакого unrestricted subnet sweep. |
| M3.5c (secure mode) | Фактический server/client security profile, versioned TOML/invite, server identity, replays, active probing rejection, strict fallback, runtime/IPC and negative network E2E |
| M3.5d (TLS-in-TLS) | Bounded flow-shaping исследование и реальный pipeline; classifier/benchmark gate, отрицательные сетевые случаи и measured overhead, separate H2/H3 evidence |
| M4.5 (two-action TUI) | Серверный мастер Проверить и подобрать → Применить + безопасный preview, rollback/status, F-14 export; клиентский импорт и строгая проверка |
| M5 release | Требования F-18/F-19 приняты **только после** real Linux-server/Windows-client E2E, крипто/безопасность review, reproducible browser/stealth/TLS-in-TLS comparisons и CI gates |

Все CI проверки автоматические, никакой ручной обязательной проверки. Статус до этого: **experimental/unreleased, REALITY-like и TLS-in-TLS protection не реализованы**.
