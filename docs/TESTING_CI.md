# Testing strategy и CI

**CI release-сборки только по явному запросу (24.11.2026):** обычные PR и push в `main` больше не запускают в конце Linux `rust-tests` и Windows `windows-smoke` лишние `cargo build --workspace --release --locked`. Эти оптимизированные бинарники не публиковались, и обязательный F-14 E2E использует предварительно собранные native debug/dev ELF/EXE из тех же проверенных заданий. Обязательная матрица, cross-SID kernel DACL, WinINet, ConPTY, WSL2 Linux→Windows и `ci-gate` остаются без пропусков на кодовых изменениях. Для проверки **обоих release-профилей** используйте GitHub Actions → **CI (tests first)** → **Run workflow**: `workflow_dispatch` запускает полную проверку и обе оптимизированные сборки. Это проверка компиляции, не автоматический выпуск артефактов. См. `docs/CI_PERFORMANCE.md` и регрессионный `tests/ci/check_workflow_parallel.py`.

**CI exact-head и fail-fast (CI speed-up, 24.11.2026):** CI теперь НИКОГДА не переписывает PR после тестов. `specification` перед дорогими Rust/Windows job проверяет `cargo fmt --check` (root + оба spikes), `gofmt -l` и неизменность исходников. Format drift прерывает запуск ещё до Linux/Windows fan-out; никакого `ci-formatted-source`, per-job overlay, `persist-format` с бот-коммитом или непроверенного нового SHA. `ci-gate` всегда относится к тому же git tree, который был проверен. Исправить форматирование нужно **до** PR, иначе preflight намеренно падает. Задания по-прежнему делают собственные Rustfmt/Clippy checks, а release/CI продолжают требовать exact-head success.

**Safe trace logger / ADR-0058 (pending exact-head CI):** в native Linux/Windows CLI tests каждый `theia` процесс по умолчанию создаёт отдельный приватный локальный trace. Проверяются disable `THEIA_TRACE_OFF=1`, отсутствие переданного секретного параметра в логе, ротация двух сегментов с суммарным ограничением 50 МиБ и UNIX 0700/0600. Native Rust jobs задают `THEIA_TRACE_DIR=${{ github.workspace }}/theia-traces` и при failure загружают диагностические файлы в artifacts на 3 дня. Это не wire capture: не писать header/token/target/payload ни в CI, ни на клиенте/сервере. Файлы предыдущих запусков требуют отдельной очистки.

**M4.4d cross-OS acceptance (PR #85, CI pending):** Новый обязательный `f14-cross-host` job получает ровно тот Linux ELF `theia`, который построен в обычном Ubuntu `rust-tests` job (same-run artifact), и поднимает его в отдельной WSL2 Ubuntu VM на нативном Windows 2025 runner. Это **реальное Linux-ядро, отдельное виртуальное сетевое устройство и Windows-клиент на хосте**, не два отдельных публичных/физических сервера. Отсутствие WSL2, non-loopback IP, Linux ELF или доступного TCP listener приводит к ошибке, никогда к skip. Windows CI создаёт случайный 256-битный bearer, передаёт Linux только SHA-256 digest, использует production `Invitation::issued_from_server` и `Editor::import_invitation`, проверяет отдельный private bearer file, inactive profile, явный выбор профиля и строгий отдельно предоставленный CA. Скомпилированный Windows `theia.exe client run` делает настоящие HTTP CONNECT и SOCKS5 H2/TLS и UDP/H3/QUIC к Linux-серверу с реальным `OPEN_OK`, byte-exact 128KiB relay и half-close. Неверный bearer или CA никогда не дают CONNECT 200 или SOCKS5 success, duplicate ID отвергается, WinINet остаётся off. Windows client и его F-14 integration test harness передаются как артефакт **из уже выполненного обязательного `windows-smoke`** после его полного `cargo test --workspace --all-targets`; Linux ELF передаёт `rust-tests`. В отдельном WSL2 acceptance job **не выполняется `cargo build` или `cargo test`**: ранее скомпилированный Windows тестовый executable запускается напрямую и использует переданный prebuilt `theia.exe`. Обязательный `specification` preflight выполняет `compileall` и Python unit проверку выбора гостевого IPv4 до дорогих Rust сборок; исправлена ошибка `ip.is_loopback()` (свойство, а не функция), выявленная в CI #45271527921 после шестиминутной Windows-компиляции. Этот job включён в final `ci-gate` наряду с остальной обязательной матрицей. **Отдельная физическая Linux VM → Windows VM через удалённую сеть, SSH/TUI выдача, NAT/firewall, long-lived Windows profile и расширенная crash/ACL матрица ещё НЕ закрыты**: F-14 release acceptance остаётся открытым.

**CI Linux root fingerprint deduplication (24.11.2026):** `m0-1-api-spike (Linux)` больше не исполняет `cargo test --workspace --test fingerprint_h2` из независимого каталога spike, где это **повторно компилировало весь root workspace**. `rust-tests (Linux)` после обязательного `cargo test --workspace --all-targets --locked` запускает тот же pinned Go uTLS Chrome133 fixture и `fingerprint_h2` на **уже собранном** бинарнике. M0.1 по-прежнему выполняет собственные Go/rustls transport, reference и PKI tests, а повторная тяжёлая root-компиляция исключена без ослабления Linux coverage. Эффект на длительность измеряется по completed PR runs.

**CI Windows Go/uTLS critical-path optimization:** В `m0-1-windows-spike` остаются независимые M0.1 TLS/H2/QUIC/Go tests и генерация закреплённого Go uTLS 1.8.2 Chrome133 reference, но он более НЕ запускает `cargo test --workspace --test fingerprint_h2` и не собирает весь root workspace вторично. После обязательного `cargo test --workspace --all-targets --locked` этот fingerprint test выполняет `windows-smoke` с отдельно сгенерированным и проверенным `go mod verify` эталоном той же версии. Это использует уже собранный root Rust test executable, сохраняет Linux/Windows coverage и параллельный DAG. `specification` запускает дешёвый `python3 -m compileall -q scripts tests` до любых тяжёлых сборок. По профилю CI от 23 ноября 2026 года прежний Windows M0.1 Go-reference шаг тратил 5m29s на повторную root Rust compilation даже при попадании в Go cache. Новый выигрыш измеряется по полному CI, не предполагается заранее.

**CI docs-only fast path (CI speed-up, 24.11.2026):** только PR/push, где Git доказывает изменение исключительно `docs/**/*.md` и разрешённых корневых README/CHANGELOG/CONTRIBUTING `.md`, пропускают тяжелую native Linux/Windows/Go/WSL2 матрицу. При этом `specification` выполняет TOML/docs contracts, CI DAG checks, Python security unit tests и проверку conservative scope; финальный `ci-gate` требует **success** specification и **skipped** каждого native job. Изменения `.github/workflows`, `scripts/`, `tests/`, Rust/Go/lockfile, смешанные PR, пустой diff, неизвестная история, недоступный base или workflow_dispatch всегда запускают ПОЛНЫЙ native CI. Не используется сторонний action, списки путей не выполняются как shell-команды. Для code PR и любых сомнений сохраняются все строгие CA/SAN/ALPN, BBR, Chromium, Windows SID/ConPTY, Linux PTY, F-14 cross-host H2/H3, rustfmt и Clippy gates.


**M4.2l bounded TLS rollback CI (ADR-0052):** Mandatory Linux+Windows compiled-server E2E начинает с отсутствующего rollback slot (check и apply должны fail closed), делает реальную H2/H3 same-port TLS rotation 1→2; `server tls rollback --check` возвращает ревизию и остаток из 300 секунд без приватного материала. Auth-only CAS 2→3 оставляет recovery доступным, stale apply для revision=2 запрещается. Повторная TLS rotation 3→4 обновляет slot. После неё test намеренно портит PEM прежней TLS identity на диске, но явно подтверждённый `server tls rollback --apply --expected-revision 4 --confirm` обязан вернуть предыдущий сертификат для реальных новых H2/H3 handshakes с сохранением нового токена, revision=5 и без повторного открытия PEM; повторный rollback=5 отвергается. Unit test bounded readiness проверяет expiry, CLI запрещает неканоническую revision, отсутствие --confirm и лишние flags. Standalone IPC не включает rollback, cross-SID kernel DACL, ConPTY/Linux PTY, Chromium Linux/Windows, BBR/BoringSSL, Rust fmt/Clippy и exact-head 14/14 final ci-gate обязательны. Нет automatic health-based rollback, fresh-port reversal, гарантий глобального TLS handshake cutover или persistent rollback history.

**M4.2k PEM content pin (ADR-0051):** Real native Linux/Windows compiled H2/TLS+QUIC/H3 restart E2E on original protected IPC: read-only local `server tls fingerprint --config FILE` returns ONLY a domain-separated, length-prefixed SHA256 digest of loaded cert/key bytes (no secrets). After it is calculated, test overwrites candidate PEM paths with another VALID matched cert/key pair and leaves TOML untouched; `server restart --apply --expected-revision N --sha256 TOMLHEX --tls-sha256 OLDPEMHEX --confirm` must fail closed, preserve old H2/H3 sessions and revision. Restoring approved PEM allows both same-port identity rotation and fresh-port listener cutover. Unit loads all cert/key PEM into zeroized snapshot, corrupts disk files after capture, and builds BOTH real H2 and H3 configurations FROM CAPTURED MEMORY; fingerprint changes with inbound order. Reject legacy restart Apply with missing PEM pin, uppercase/short hashes, missing --confirm; still require native Windows SID kernel denial, ConPTY, Chromium, BBR/BoringSSL/uTLS, fmt, Clippy and exact-head 14/14 ci-gate. Quota-only and auth-only Apply contract unchanged.

**M4.2j occupancy-aware live quotas (ADR-0050):** Mandatory native Linux и Windows compiled server E2E поднимает настоящий H2/TLS и H3/QUIC, удерживает два authenticated tunnels при initial global/per-user cap=2, затем через private IPC выполняет read-only quota --check, отказы wrong SHA/invalid policy/mixed edit, подтверждённый live quota CAS 1→2 на cap=1. Оба старых H2/H3 туннеля остаются живы, новые TCP+QUIC sessions отвергаются до погашения occupancy debt. Далее CAS 2→3 увеличивает лимиты до 4: дополнительные H2/H3 streams доступны без смены порта, старые туннели передают byte-exact echo. Последующий auth-only CAS 3→4 подтверждает корректный rebased baseline. Unit тесты ledger проверяют shrink ниже occupancy, разрешение после release, growth выше initial capacity, per-user/global независимые caps, connection cap и конкурентное admission/resize (8 threads). Перед ревью обязательны exact-head 14/14 CI (Rust fmt/Clippy, Windows ConPTY/SID DACL, Chromium на обеих ОС, BBR и BoringSSL). Это НЕ hard revoke и не изменение user roster/non-quota policy.

**M4.2i native same-port TLS rotation E2E (ADR-0049):** В mandatory Linux и Windows all-target compiled-server tests реальный сервер с private IPC получает два CA и два TLS1.3 cert/key на одном TCP/H2 и UDP/H3 портах. Old H2/H3 authenticated tunnels удерживаются через смену identity; неверный SHA, недопустимое изменение quota и bad cert/key дают отказ при неизменной revision=1. Read-only `restart --check` показывает same-port ready без side effects. Подтверждённая restart Apply публикует revision=2 без повторного bind, новые H2/H3 handshakes успешно проходят **только с новым CA** на прежних портах, старые authenticated tunnels завершают echo, а auth-only CAS на новом TLS baseline публикует revision=3. Должны пройти Linux fmt/Clippy, native Windows ConPTY, different SID DACL, browser E2E обеих ОС и final exact-head 14/14 ci-gate. TLS handshake race across transports, PEM content pin, quotas и post-commit rollback остаются за пределами этого этапа.

**M4.2h real supervised restart E2E (ADR-0048):** Native Linux + Windows test запускает compiled Theia H2/TLS+H3/QUIC server на loopback, native private IPC, реальные H2/H3 туннели к local echo. Негативные проверки: неверный SHA, занятый TCP, занятый UDP, изменение quota, повторное использование старого адреса, out-of-band TOML edit и stale expected revision: каждый отказ сохраняет revision=1 и доступность old H2/H3. Позитивный **подтверждённый** SHA-bound fresh-port TLS cutover публикует revision=2, новые H2/H3 server endpoints действительно принимают authenticated tunnels, старые ранее авторизованные соединения заканчивают в bounded 20s drain, новые запросы в retired generation запрещены, а последующий штатный auth-only CAS публикует revision=3 на новом listener generation. Проверяется CLI обязательный --confirm, строгая digest/revision canonicalization, сохранение global/user quotas между поколениями и stale IPC safety. Не утверждать same-port TLS restart, quota/roster cutover, session migration, full rollback или отсутствие прерываний после commit. Должны пройти все 14 CI jobs (включая Windows cross-SID, ConPTY и final ci-gate).

**M4.2g restart readiness E2E:** На реальном скомпилированном H2/TLS+QUIC/H3 сервере с private native Linux IPC / Windows SID Named Pipe операторская CLI `theia server restart --check` проверяет стартовый cert/SAN/key, новый typed TOML, native simultaneous new TCP/UDP binds; один занятый TCP или UDP, неверный SAN/PEM и отсутствие IPC должны дать отказ. Повторное использование прежнего bind при смене квот даёт только `maintenance`; auth-only совместимый кандидат предлагает существующий CAS. Каждая ветка перепроверяет статус неизменной revision=1 (действующие H2/H3 listeners продолжают служить); затем настоящий Linux PTY / Windows ConPTY по Shift+R показывает read-only restart-review без публикации от клавиш y/a, после чего старая terminal TUI выполняет настоящий CAS Apply 1→2, без ослабления старых тестов. Unit-case wildcard/dual-stack и отказ второго одновременного restart probe. Никаких автоматических restart, port reservation после проверки, TLS rebind или ложного обещания rollback: это advisory readiness и будущий supervisor остаётся PENDING (ADR-0047). Для exact-head обязательны 14/14 ci-gate Linux/Windows native smoke.

**CI critical path optimization (ADR-0046):** после specification запускаются параллельно native Windows smoke, Linux rust-tests и обе Chromium browser-e2e ОС, поскольку они не используют результаты друг друга; дополнительный rust_ready guard browser matrix сохраняет semantics specification-only. Финальный ci-gate с always() по-прежнему требует success всех обязательных job (включая kernel DACL другой SID, реальный Windows ConPTY/Linux PTY, браузерные и исследовательские E2E). Все три test-only setup-go используют Go module/build cache по закреплённому spikes/m0_1/utls_reference/go.sum. В specification исполняется автономный CI DAG regression tests/ci/check_workflow_parallel.py, который проверяет точные зависимости и защитные условия. Baseline workflow PR #70: Linux rust-tests ~95 с; Windows smoke стартовал только после них, затем ~139 с, ci-gate около 13:59:41 UTC. Параллельный запуск устраняет DAG wait, но фактическое ускорение нельзя обещать без измерения run-to-run на загруженных runner; cache miss и конкуренция за runners могут дать иное время. Первичная проверка red: https://github.com/iivkis/theia/actions/runs/45190013448, exact-head green должен быть отдельно подтверждён.

**M4.2f real PTY/ConPTY TUI E2E:** Native Linux и Windows cargo integration test запускает настоящий compiled TLS/H2 + QUIC/H3 loopback server с private Unix socket / SID Named Pipe, затем отдельный скомпилированный TUI в ОС-псевдотерминале: Linux PTY из стандартной библиотеки Python, Windows ConPTY c test-only закреплённым pywinpty 3.0.5 (устанавливается до windows-smoke). Отображение оценивается через pinned pyte 0.8.2 с ANSI VT-экраном: разреженная перерисовка ratatui не приравнивается к полному исходному тексту. Реальные Ctrl+R/n/a/y, ожидание видимых модалок, фактический CLI status до и после подтверждения (CAS revision 1→2), строгое SHA-256 содержимого при внешней записи TOML (Reject), несохранённый черновик, клиентская роль/no-config, восстановление alternate-screen и нормальный exit. Никакого тестового IPC-фейка, skip, ручной терминальной проверки или публикации полного PTY вывода с потенциальным секретом; удалённый SSH ещё открыт (ADR-0045). До успешного exact-head ci-gate это критерии, а не подтверждённые результаты.

**M4.2e Windows cross-logon Named Pipe ACL security E2E (CI-only):** обязательный шаг windows-smoke запускает scripts/windows-cross-sid-ci.ps1 с одноразовым непривилегированным локальным пользователем и реальной проверкой Win32 CreateFileW под вторым TokenUser SID. Требуется положительный контроль: второй пользователь успешно открывает пустой test-only локальный pipe с Everyone DACL. Только затем kernel ERROR_ACCESS_DENIED=5 при открытии точного SID-scoped pipe работающего WindowsServer считается успехом; отсутствие pipe, timeout, недостаточные права CI на создание аккаунта и same-SID логон обязаны падать. Успешный same-SID status подтверждается первым, аккаунт удаляется в finally; runtime/TLS/TOML/proxy не меняются (ADR-0044). До exact-head CI это только добавленный сценарий, не подтверждённый результат.

**Правило CI-only:** все проверки выполняются автоматически в GitHub Actions. Разработчик и пользователь не должны запускать тесты или вручную подтверждать сценарии. Тестирование предшествует сборке релизных артефактов. CI не должен маскировать отсутствие сетевой Rust-реализации. С M1.1 корневой workspace и `Cargo.lock` существуют: Linux `rust-tests` и Windows `windows-smoke` должны запускаться. CLI `--help`/`--version` работают; с M1.2 `config validate` выполняет структурную TOML v1 validation (exit 0/2) без чтения секретов. Команда `tui` (M4.1a) запускает только read-only ratatui навигацию при интерактивном TTY; без TTY возвращает ненулевой статус без сетевых и системных эффектов; M2.2b добавляет `client run` в explicit H2 (CI pending); с M2.1 `server run` — реальный TLS1.3/H2 сервер с bearer/inbound ACL + TCP dial и ненулевым exit на invalid config/PEM. До M1.1 Rust jobs были skipped.

**M3.5b2b1 collector CI:** `crates/theia/tests/camouflage_interfaces.rs` проверяет локально обнаруженный Linux loopback, mask provenance, отказ от эмуляции NAT egress, непрерывные IPv4/IPv6 masks и негативные noncontiguous/zero masks; Windows гарантированно компилирует model и возвращает Unsupported (не пропускает тест). Ни один тест не обращается к внешним серверам или не требует ручных IP/CIDR, режим scanner не включён. Дополнительный native Windows collector остаётся отдельным этапом.

**M3.5b2b2 native Linux/Windows mandatory tests:** `crates/theia/tests/camouflage_egress.rs` проводит настоящие TLS1.3/http1.1 handshake с локальными CI-only сертификатами, проверяет явный pinned exact-socket consent, нормальный IPv4/IPv6 IP echo, timeout, неверный CA/SNI/ALPN, redirect, private/doc IP ответ, пустой trust store и HTTP injection rejection. Никаких сторонних сервисов, DNS или автоматического сканирования. `crates/theia/tests/camouflage_workflow.rs` проверяет пассивный план vs одобренный маленький CIDR, реальную /32 блокировку, фильтр down/invalid/private interface, native Linux collection и Windows Unsupported. Успех всех обязательных job + `ci-gate` только на exact head SHA.

**M3.5b2b3 bounded exact-target batch CI (Linux/Windows):** `crates/theia/tests/camouflage_batch.rs` создаёт только loopback TLS1.3 fixtures и проверяет позитивный одновременный H2 batch, порядок результатов, независимые негативные TLS/ALPN/timeout ответы, all-handshakes fail-closed, отказ при отсутствии явного разрешения, IP вне offline preview, duplicate socket, пустой и превышающий лимит списки. Публичная сеть/DNS/seed домены не затрагиваются; runtime scanner/UI отсутствует. Обязательные `cargo test/fmt/clippy`, ОС-матрица и точный `ci-gate` должны быть успешны.

**M3.5b2b4 default ipify CI:** `crates/theia/tests/camouflage_default_ipify.rs` проверяет точный URL `https://api64.ipify.org/`, path `/`, установленный лимит времени, отсутствие DNS/сети при `IpifyConsent::Denied` и отсутствии CA, реальные loopback TLS1.3/http1.1 fixture с сертификатом/SAN `api64.ipify.org`, правильные Host/SNI, IPv4/IPv6 plain-text ответы, запрет private-IP и отсутствие утечки hostname через Debug. Windows/Linux обязательны; никаких реальных запросов к ipify в CI. Только положительный `ci-gate` на финальном SHA разрешает merge.

**M4.5a TUI consented discovery CI:** pure state-machine/tui tests verify p on server screen opens **passive** native interface+14 domain preview, no worker/DNS by default, i shows disclosure for exact `api64.ipify.org`, n denies, Esc drops/cancels flow, client/Home/Help cannot trigger discovery, dirty typed TOML editor refuses navigation. `tui_discovery` tests verify no worker starts before explicit confirmation and safe cleanup. ## 1. Test pyramid

### A. Pure unit tests (самые быстрые, обязательны в каждом PR)

- SmartTheia encode/decode golden byte vectors; arbitrary chunk splitting/aggregation; frame length 0/65536/65537; invalid flags/type/state; отсутствие паники и out-of-bounds. С M1.3 — `crates/theia/tests/protocol.rs` с реальными golden-byte assertions, per-stream client/server FSM, strict OPEN_OK gate, half-close/abort и deterministic malformed-byte regression. Настоящий coverage-guided fuzz и transport E2E остаются за пределами pure codec PR.
- Typed TOML: missing/unknown fields, duplicate IDs/hashes, bind collisions **including wildcard overlap and IPv6 dual-stack**, malformed DNS/IPv6/port, unsupported schema_version, UTF-8 errors, missing secret refs, empty user list, диапазоны таймаутов, **missing/empty/unknown/duplicate allowed_user_ids**, запрет `system_proxy=on`, отказ неизвестного `tls_profile`.
- Transport selector: строгая таблица классификации `UdpUnavailable` versus `TlsVerificationFailed`/`Unauthorized`/`IncompatibleProtocol`/`PolicyDenied`, negative-cache TTL, cancellation, no re-dial after downstream error.
- Policy: IPv4/IPv6 public/private, loopback, link-local, multicast, DNS rebinding after resolution, case folding/IDNA validation.
- TUI update model: keyboard, focus, dirty state, save and apply distinct, privacy masking, compact terminal, back navigation.
- Windows system proxy: adapter fake с сохранением оригинальных proxy/PAC настроек, compare-and-restore, отказом прав, повторным apply и simulated crash.

### B. Integration tests (локальный реальный IO)

- TLS-backed H2 echo tunnel, multiple concurrent streams, **full-duplex HTTP POST without request EOF**, half-close, abrupt EOF, timeout, bounded backpressure, broken clients and error mapping. С M2.1 `crates/theia/tests/server_h2.rs` проверяет реальное TLS1.3/H2 OPEN_OK→echo + half-close, missing bearer HTTP401, private ACL OPEN_ERROR без dial, strict wrong-hostname TLS и pure auth/IP ranges. **Дополнительные** many-stream/race/cancellation/slow-reader/peak RSS и DNS rebinding fixtures ещё не закрыты. Loopback echo тестировать только с explicit test-only `allow_private_ips=true`; отдельный negative test обязан подтвердить default=false.
- H3 echo tunnel via UDP loopback, full-duplex request/response, certificate validation, resumption/0-RTT disabled, **BBR на обоих отправителях как P0 release gate** (никаких `pending` при объявлении MVP).
- Fallback H3→H2 с симуляцией/блокировкой UDP; ни одного H2 retry при wrong cert/auth/protocol mismatch.
- HTTP CONNECT + SOCKS5 local proxy с server-side DNS, IPv4/IPv6, отказом auth и неразрешённым адресом. HTTP 200/SOCKS5 success должны приходить **строго после OPEN_OK**; неверный токен другого inbound не получает доступ; имена не резолвятся локальным клиентом.
- IPC auth/ACL (Unix socket/Windows pipe), atomic config reload, сохранение старого runtime при failed apply.
- Windows per-user proxy smoke: автоматические Windows runner tests для API adapters и отдельный автоматический сценарий на изолированном временном Windows-профиле/VM: snapshot, apply, CAS restore, конфликт и восстановление после аварии. Запуск и teardown средствами CI; до реализации сценария M4.3 и соответствующий release gate остаются открытыми. Не менять настройки пользователя или обычного runner.
- No external production endpoints in CI; TLS сертификаты для теста генерируются в памяти/fixtures, без реальных секретов.

### C. Property/fuzz + security

- Property-based encode/decode roundtrip с фиксированными seeds в CI; fuzz parser в автоматическом scheduled CI после реализации fuzz targets; никаких обязательных ручных запусков.
- Limit tests для frame headers, header counts, slowloris, concurrent streams, open proxy и unauthorized requests.
- Tests negative TLS: expired, wrong hostname, untrusted CA, mismatched key.
- Test deny private ranges **после** DNS resolve, исключить попытки установить запрещённое соединение.

### D. Performance и fingerprint (не «успех по словам»)

- Измерять throughput по H2/H3 и RTT p50/p95 при одинаковых payload/host, CPU, peak RSS, количество аллокаций, потери при 1%/5%, число H3→H2 fallback.
- CI не должен запускать шумные full benchmarks при каждом PR. Baselines автоматически измерять и сохранять как CI artifacts в стабильном изолированном benchmark runner перед релизом. Пока соответствующая автоматизация не реализована, release gate открыт.
- **P0 gate F-13:** M0.1 baseline `spikes/m0_1/tests/client_hello_baseline.rs` измеряет default rustls ClientHello для TLS/H2 (TLS record) и QUIC/H3 (plaintext CRYPTO before encryption), выводит IDs/ALPN и не пишет SNI/random/session ID. Это НЕ browser pcap, не named profile. Вместо захвата эталонного браузера CI генерирует HelloChrome_133 ClientHello из **Go uTLS v1.8.2** (H2/TLS) и сверяет его с rustls: GREASE, ALPS, supported_groups, наборы шифров и ALPN. Для H3 требуется отдельный QUIC-совместимый референс. Release gate по-прежнему требует сравнить **фактически испускаемые Theia** H2/H3 TLS/QUIC handshakes, H2 SETTINGS и H3 SETTINGS/QUIC transport parameters с релевантными эталонами и зафиксировать расхождения. Go-генератор и отдельный test-only Go uTLS сетевой клиент не заменяют работающий Rust fingerprint backend. M0.1 дополнительно проверяет настоящий Go uTLS Chrome133 TCP/TLS 1.3 H2 GET→Rust h2 HTTP 204, GREASE/ALPS на сокете и fail-closed wrong-hostname/untrusted-CA на Linux и Windows. Публиковать поддерживаемые параметры и различия, а не только «успешный» тест.
- Проверка BBR: идентификация конкретной реализации congestion controller и сравнительные loss/jitter benchmarks, а не только строковый параметр в TOML.

## 2. CI pipeline

Файл: `.github/workflows/ci.yml`.

1. `specification` (Ubuntu, самый быстрый): проверить файлы, локальные Markdown links, оба TOML и invariants; определить есть ли одновременно `Cargo.toml` и `Cargo.lock`.
2. `rust-tests` после specification: Rust toolchain + cache, `cargo test --workspace --all-targets --locked` **первым**, только после успеха `cargo fmt`, `cargo clippy -D warnings` и `cargo build --release`.
3. `windows-smoke` после Linux tests: Windows-native `cargo test` и `cargo build --release` с отдельным кэшем. Системные proxy settings на GitHub-hosted runner без явного sandbox-плана не менять.
4. Кэш: `Swatinem/rust-cache@v2` для registry/git/target, `Cargo.lock` как источник cache key; concurrency отменяет устаревшие runs на одной ветке. Запуск на push и PR.
5. Rust jobs **skipped**, пока нет production workspace; как только добавлен корневой `Cargo.toml`, отсутствие корневого `Cargo.lock` становится ошибкой CI, а не silent skip.
6. **M0.1 в отдельном `spikes/m0_1`**: `cargo test --manifest-path spikes/m0_1/Cargo.toml --locked` на Ubuntu и Windows, кэш по отдельной директории, без включения spike в поставляемый бинарник. `Cargo.lock` находится в каталоге spike и зафиксирован в git. Успех M0.1 transport tests подтверждает **H2/TLS и H3/QUIC/TLS E2E** (real loopback, TLS name+ALPN verification, body before request EOF), а также **H2/TLS 1 МиБ flow-credit + half-close**, **QUIC BBR byte-exact recovery с детерминированными 1/20 synthetic outgoing datagram drops**, **H2/H3 по 8 одновременных stream и отмену одного запроса без разрыва общей защищённой сессии**, **H2 slow response reader 512 КиБ и H3 slow response reader 1 МиБ с остановкой/восстановлением передачи при малом flow-control budget**. Это не закрывает release gates: **comparative BBR loss/jitter/pacing/throughput benchmarks, many-stream cancellation and many-slow-readers stress/peak RSS limits, SmartTheia auth/ACL tunnel, Go uTLS H2 reference + отдельный H3 QUIC эталон + реальная browser-like настройка Theia**. Отрицательные TLS tests: wrong name, untrusted CA, ALPN mismatch.

## 3. Проверки только в CI

Workflow автоматически запускается для PR, обновлений PR и push в main. Команды тестов, линтов, сборок и генерации fixtures принадлежат CI jobs, а не инструкции пользователю. TDD: red test подтверждается автоматическим PR-run до исправления, green run после реализации. Если тест нестабилен, устранить nondeterminism.

Тяжёлые benchmark/fuzz/GUI/OS recovery сценарии автоматизируются отдельными scheduled/release workflows по мере реализации; штатная проверка не требует ручного запуска. Использовать временные профили, loopback/изолированные сети, ephemeral credentials, автоматический cleanup и машинно-проверяемые assertions. Будущие автоматические security/audit checks также не требуют локальных команд. До появления и успеха необходимой автоматической проверки соответствующая функция не считается готовой.

Статус `ci-gate` агрегирует результаты шести групп jobs текущего workflow (browser-e2e включает два обязательных runner). Failure, skipped и cancelled обязательного job запрещают зелёный gate. Это не заменяет будущие ещё не реализованные release jobs. Для приёмки учитывать успешный run именно проверяемого head SHA, а не старого коммита.

## 4. Правила мержа и качества

Для branch protection использовать итоговый required check `ci-gate` на main. Настройка branch protection является отдельной настройкой GitHub, а не ручным тестированием; документ не утверждает, что она уже включена. Запретить merge при красном CI, секретах, расхождении wire/TOML с docs и непокрытых негативных тестах. Не требовать сборку бинарников от docs-only состояния.

Каждый релиз требует автоматическую CI-матрицу Linux server + Windows client на изолированных runner/VM, временный доверенный сертификат, ревокацию токена, fallback при недоступном UDP, отказ при wrong cert, автоматическую Windows proxy recovery и documented limitations. Пока обязательные проверки не реализованы и не прошли в CI, релиз не допускается.


M2.1 hardening: preflight certificate SAN matches configured DNS name (not full PKI chain/time validation), bounded shared IP request budget (120/min; 4096 peers; fixed windows; all requests), 8 KiB H2 header limit, H2/TLS handshake deadlines, single DNS/dial deadline with at most 64 results, task ownership via JoinSet, and bounded abort/drain. Remaining stress and full PKI checks are not claimed complete.

M2.1 relay regression: independently driven TCP read/write halves, bounded H2 frame send, direction-specific FSM checks, stream reset on interrupted wire frame. Production-server integration tests exercise withheld response credit (1 KiB H2 window, 256 KiB download, successful concurrent upload and FIN) and eight open tunnels on one H2 connection with one cancelled stream and byte-exact sibling transfers. These are bounded regression tests, not a peak-RSS or large-scale benchmark; await Linux/Windows CI.

M2.2a: production client core tests in `crates/theia/tests/client_h2.rs` exercise TLS1.3/H2 against the real server, DNS OPEN_TCP, 256 KiB byte-exact relay/FIN, wrong hostname/untrusted CA/token and private ACL denial before any target dial. Trust roots are explicitly injected in this slice; no local listeners or client CLI/runtime yet. Tests use ephemeral loopback certificates, not TLS verification bypass.

M2.2b adds automated local CONNECT/SOCKS5 loopback regression against production H2 client/server. Local success is emitted only after OPEN_OK, policy rejection returns HTTP403/SOCKS REP2, CONNECT does not consume pipelined bytes. Tests run only in CI. Explicit CA + env/file token runtime, no default platform roots or auto/H3. Browser/curl and OS-specific automation remain open; no user smoke test required.

M2.2b black-box CI: `client_binary_curl_connect_and_socks5h` launches the built `theia client run` with a temporary TOML, generated trusted PEM and child-only env token. Real curl uses HTTP CONNECT (`--proxytunnel`) and SOCKS5h, receives exact HTTP origin bytes on loopback, bypass disabled. Native Linux/Windows runner commands are mandatory (missing curl fails); subprocesses/fixtures cleaned up automatically. Browser automation is added in the mandatory browser-e2e matrix, pending CI.

Chromium CI: `browser-e2e` runs the pinned Playwright 1.65.2 Chromium fixture on Linux and Windows. A test-only SOCKS gate limits destinations to the generated loopback origin and forwards the permitted request to the running Theia client, then verifies HTTP 200, DOM marker and actual SOCKS success.
