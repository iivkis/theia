# ADR-0019: M4.4b1 — создание серверного пользователя и одноразовая ссылка

**Дата:** 2026-11-22. **Статус:** реализация в PR #43; требуется exact-head CI.

## Решение

Серверная TUI на удалённом Linux-хосте (например, по SSH) с явным ролью и валидным TOML позволяет выбрать existing inbound и нажать `u`. Вводится новый ID пользователя, подтверждается создание; новый 32-байтный bearer генерируется через rustls/ring SecureRandom (без новых генераторов), сервер сохраняет только SHA-256 от исходных байтов, запись disabled=false и grant исключительно в выбранном inbound. Весь typed Config перепроверяется, серверный TOML атомарно записывается через существующий one-shot worker.

До успешной записи файлa и **второго** подтверждения ссылка theia://v1 с bearer скрыта. Неуспешное сохранение (включая внешний конфликт) разрешает только повторную попытку либо отмену с уничтожением черновика. После успешной записи оператор может один раз раскрыть секретную ссылку на экране или отказаться; после Esc повторный показ невозможен. Из старого SHA-256 исходный bearer нельзя восстановить.

## Ограничения и риски

- Никакого reload, подключения, HTTP control plane, Windows system proxy или изменения схемы/wire. Пользователь из нового server.toml может ещё не существовать в работающем runtime.
- Секрет защищён best effort через zeroize для временного RNG-массива, байтов Invitation при Drop и показываемого Zeroizing<String>. Вспомогательные буферы serde/base64, терминальный scrollback и SSH-трансляция могут сохранять данные: гарантированного стирания среды нет. Нужен доверенный терминал и подтверждённая оператором передача.
- Это создание **новых** пользователей: ротация/отзыв существующих, защищённый файл, clipboard/QR, надёжное копирование длинных URI, client import и кроссплатформенное OPEN_OK E2E остаются будущими срезами. При отказе от просмотра токен теряется без возможности восстановления.
- Проверка неизменности внешнего файла до сохранения best effort, не защита от враждебной race в недоверенном каталоге.

## Критерии приёмки

Native Linux/Windows CI проверяет создание пользователя и grant, сохранение только digest, независимые токены CSPRNG, невозможность выдачи на второй inbound, невалидные/повторные ID, грязный черновик, сбой файла и отсутствие ссылки до success, отдельный reveal, закрытие модалки и ролевую изоляцию. Остальные обязательные H2/H3, BBR, TLS fingerprint, Chromium E2E и aggregate ci-gate на точном SHA должны оставаться зелёными.
